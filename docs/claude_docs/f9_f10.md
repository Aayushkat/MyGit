# Feature 9 & 10 — Extended Theory & Field Notes

> **What this is:** the layer underneath F9 (vanilla HTML/CSS/JS frontend) and F10 (React). How the browser's event loop actually runs your JS, why `fetch` is not "just a function call", what XSS really *is* and why `textContent` disarms it, what "the DOM" is, and what React's virtual DOM/reconciliation *mechanically* does that F9's manual rendering didn't. Read it after you've built both frontends once.
>
> Two kinds of additions live here: **theory** (the mechanism underneath something the original doc told you to just do) and **field notes** (bugs, silent failures, and the gap between "works on my machine" and "works under real traffic").

## Part 1 — Feature 9: Vanilla Frontend (HTML/CSS/JS)

### 1.1 The browser is another HTTP client — the symmetry that makes it click

F2 will have taught you "our server is a client of GitHub's server." F9 is the mirror: **the browser is a client of your server.** The *same* HTTP round-trip shape — request line, headers, body, status, headers, body — happens between the browser's `fetch()` and your FastAPI endpoint as happened between your httpx client and GitHub. Nothing new is being invented; the roles are just rotating again.

That symmetry is what makes the whole system teachable. The mechanism on the frontend:

```js
fetch(`/api/v1/users/${username}/portfolio`)   // sends HTTP GET
  .then(res => { ... res.status, res.ok ... }) // reads the RESPONSE LINE + STATUS
  .then(data => { ... });                       // parses the BODY
```

`res.ok` is `res.status >= 200 && res.status < 300` — the exact status-class logic your Python client used. Errors surface as *status codes*, not thrown exceptions — this is why checking `res.ok` is mandatory and why FastAPI's standardized error shape (the F2/F4 `{"error": {...}}`) pays rent: the frontend can read one predictable field.

The one frontend-only twist: **`fetch` returns a `Promise`, not the data.** Because a network call is I/O, and the browser's JS engine (like Python's event loop) must not block waiting — `await` / `.then()` is the JS spelling of "pause here, resume when the network answers." Same problem, same solution, different syntax.

### 1.2 The DOM, mechanisms under the hood

"The DOM" — every time you say `document.getElementById`, you're touching it. Mechanically:

- The browser parses HTML into a **tree of live objects** (elements, text, attributes): the Document Object Model.
- **`innerHTML = "<b>x</b>"`** parses that string *as HTML* and replaces the element's children with *newly created elements*. Inherently: create elements, wire them into the tree, run any scripts in the string.
- **`textContent = x`** sets a *single text node's value* — pure data, no parsing.
- Later `getElementById("name").textContent = data.user.name` *mutates one node*; the browser then **repaints only the affected part** of the page (fast, incremental layout).

This distinction — "parse as HTML" vs "set as text" — is the entire XSS story (next section). And it's also why F9's "render = set node values" is cheap: you're not rebuilding the page, just touching text nodes.

### 1.3 XSS — what it actually is, and why `innerHTML` is a loaded gun

XSS (cross-site scripting) is: **attacker-controlled data executed as code in *your* origin.** Concretely: a repo description on GitHub ("`<img src=x onerror=alert(1)>`") is just *data* from your server's perspective (a string in the JSON). If your frontend does:

```js
container.innerHTML = repo.description;   // BAD
```

then the browser **parses that string as HTML**, and `onerror=...` *executes* — inside your site's security context, able to read `localStorage`, send `fetch` requests with the user's token, and hijack the session. It's not the API that's vulnerable; it's the *rendering path* that trusted un-trusted input as code.

Two defensive mechanisms you're learning:

1. **`textContent` is structurally incapable of this.** Setting text creates a text node — the browser can't *parse* it, so it can't *execute* it. This is forcing the safe path by construction, not by vigilance.
2. **Escaping** (what template engines call `{{ }}`): the angle brackets become `&lt;` so they render as text. `textContent` does this implicitly; `innerHTML` never does.

The cargo-cult version of this lesson is "never use innerHTML." The *understanding* version is: **any time a string from an external API crosses into the HTML parser, you have an injection surface. The safe operation is "set it as text."** That sentence generalizes to every framework (React escapes by default — that's WHY it's safe — but `dangerouslySetInnerHTML` exists because sometimes you *genuinely* need to render HTML, and then you must sanitize with a library).

### 1.4 `e.preventDefault()` and the form's default behavior

Why does the doc make you call it? Because **an HTML `<form>` submission is a built-in browser behavior** — the browser navigates to the action URL with the input values serialized, *reloading the page*. For an SPA-ish page you don't want a reload; you want the JS to intercept.

The mechanism: the browser fires a `submit` event, and unless your handler calls `event.preventDefault()`, the *default action* (navigation) proceeds after your handler finishes. `preventDefault()` cancels that default — so your async fetch runs, the page doesn't reload, and you render the result. Missing it is the single most common beginner bug: the fetch DOES fire, but the browser reloads anyway and you wonder why the DOM result vanished.

### 1.5 `localStorage` — where it lives and what it is (and is not)

`localStorage` is a **per-origin, persistent key-value store living in the browser**, not in your server. Mechanism-terms:

- Keyed by **origin** (`scheme + host + port`); `http://localhost:5173` and `http://localhost:8000` are different namespaces entirely (this becomes a CORS/dev-server pain in F10's vite proxy).
- **Persists across tabs, sessions, and restarts** — unlike `sessionStorage` (per-tab) and the `cache` (per-request).
- Is **synchronous** and **string-only** (you store JSON via `JSON.stringify`, retrieve via `JSON.parse`).

Why *not* just use it for everything? Because it's **not encrypted and not safe for secrets**, and it's synchronous (the browser blocks on `getItem` for large values). "Theme preference" is exactly right; "JWT token" is a defensible-but-stateful choice some apps make; "password" would be malpractice. The boundary: **persist presentation preferences and non-secret material; never trust it as a store of record.**

### Field notes — Feature 9

> **⚠️ The "successful empty response" gotcha is worse in JS.** Your server can return `200` with `null` (f1_f2 §"A route can return None") — and `.json()` returns `null`, `null.ok` doesn't exist, and your render crashes with `TypeError: Cannot read properties of null`. Always validate the *shape* of what you parsed, not just `res.ok`.

> **⚠️ `encodeURIComponent` is the frontend's defense against path/query injection.** A username with `/` or `?` in it changes *what URL is requested*. `encodeURIComponent("a/b")` → `a%2Fb` keeps it a single path segment. F2's `Path(..., pattern=...)` rejects such usernames server-side, but the browser should *also* never craft a malformed URL — same defense-in-depth habit as F8's header sanitization.

> **⚠️ CORS bites here — before it bites in F10.** If your frontend serves from a *different* origin than your API (F10's vite dev server at `:5173` vs your API at `:8000`), the browser **blocks reading the response** of cross-origin `fetch` unless the server sends `Access-Control-Allow-Origin`. The request *fires*; the response comes back; the browser hides it from your JS. "It works from curl but not the browser" is *that* mechanism, 99% of the time. (F13 configures CORS properly.)

> **📌 Watch the Network tab when debugging — the browser is telling you the truth.** The server's response (status, headers, body) is *right there*, one click away. "But it worked twice yesterday" is a memory; the Network tab is the current truth; and `fetch`-fired requests are all visible in it. This tab will answer more questions than any debugger in this feature.

> **📌 Type your JS. "Sloppy mode" differences** (undeclared variables silently becoming globals) are the classic silent frontend bug. Since ES2015, `"use strict"` (and modern tooling) turns those into errors. F10's bundler does this for you; if you hand-write JS, type `"use strict"`.

## Part 2 — Feature 10: React (the "UI = f(state)" engine)

### 2.1 What React actually is (and the piece F9 made you feel)

The honest definition: **React is a library that reconciles a description of UI against the real DOM.** The way to make it concrete is the F9 contrast:

- In F9 you wrote `document.getElementById("name").textContent = ...` — you told the browser *how* to update, piece by piece, and you had to remember to call the right updater for every change.
- In React you write `function Portfolio({ username }) { ... return <div>{data.user.name}</div> }` — you write a **pure description**: *"given this state, the UI looks like this."* When state changes, React works out the differences itself.

The mechanism of that "it works out the differences" is **reconciliation + the virtual DOM**:

1. `setState(data)` marks the component as needing an update.
2. React re-runs the component function (your code) → produces a *new* virtual tree (a cheap JS object, not DOM nodes — this is the "virtual DOM").
3. React **diffs the old vs new virtual trees** — it compares element type, props, and children, top-down.
4. It applies *only the changes* to the real DOM (`textContent` for changed text, attribute set for changed props, create/remove for added/removed elements).

Why does F9's manual version hurt and this not? Because **you no longer hand-specify the "how."** The "how" is a fixed algorithm; you only describe the "what." That's the entire bet of declarative UI: eliminate the "I forgot to re-render after X" bug class by making re-render *automatic* whenever state changes.

The honest caveat (so you don't cargo-cult "virtual DOM = fast"): React's diffing isn't cheap magic — it's a *correctness* win much more than a performance win. It's "you can't forget to sync the DOM" pretending to be "the DOM sync is clever."

### 2.2 JSX — what it compiles to and why it's not "HTML in JS"

Look at `return <div>{data.user.name}</div>`. Mechanically, JSX is **syntactic sugar for `React.createElement("div", null, data.user.name)`** — a function call that builds a *node description object*. That's crucial to internalize:

- `<div>hello</div>` → `React.createElement("div", null, "hello")` → `{ type: "div", props: { children: "hello" } }`.
- `{data.user.name}` in JSX is a **JS expression** spliced into the children — the value is *escaped by React* (textNode-equivalent) ─ the XSS story from F9 is solved *by the tool* here.

Why "not HTML in JS"? Because it's *data describing UI*, and that data is what the virtual DOM diff consumes. The compiler (Babel/Vite) turns JSX into those `createElement` calls before the browser ever sees them. Understanding that JSX is *an expression, not a template* is what lets you grasp `{condition && <X/>}` (a JS `&&` "short-circuit returns a node"), `{list.map(...)}` (a call producing an array of nodes), and `key` (see below) without memorizing rules.

### 2.3 `useState` and `useEffect` — they're *per-render* mechanisms, and that's where the bugs live

The #1 React misunderstanding: state and effects are not "variables" — they're **hooks attached to a specific component instance, evaluated fresh on every render.**

- **`useState(initial)`** — each render returns `[currentValue, setter]`. `currentValue` is the value *captured during THIS render*. `setValue(v)` neither changes that render's `currentValue` nor "mutates a variable" — it *schedules* a re-render with the new value. Classic consequence: two rapid `setCount(c => c+1)`-style updates are *queued*, and an *old closure* holding `count` from render N sees the stale N, not N+1. (That's exactly why the functional form `c => c+1` exists.)

- **`useEffect(fn, deps)`** — runs `fn` *after* the render is committed to the DOM, and re-runs it only when `deps` changes. `deps` is a *comparison* list: on each render, React compares each dep (by `Object.is`) to the previous render's; if any differ, the effect (re)runs. The `[]` empty array means "run once after the first render." The `alive` flag + cleanup the doc gives (`return () => { alive = false }`) is the tool for the race: **when `deps` change or the component unmounts, React runs the *cleanup* of the *previous* effect run** — so `alive = false` tells a stale in-flight fetch to ignore its own result. That pattern — cleanup + "ignore late responses" — is the general mechanism for *every* "effect that fetched data that's no longer relevant" problem.

### 2.4 The virtual DOM can't do everything: `key` is not a prop

Inside `.map(...)` you write `key={repo.name}`. Mechanism: when React diffs a *list of children*, it has to decide which old node corresponds to which new node. **Without `key`, React pairs them by position** (index) — which breaks if the list reorders or filters (node 3's DOM is reused for a *different* repo, and per-render state like `useState`-in-a-list gets misattached). `key` gives React a stable identity: "this is *the same item the whole time*, even if it moved." This is the mechanism behind "why does React complain about missing keys when I `map` a list" — and it's also why the doc originally had a `def RepoList({ repos })` example putting `key` on the right element. It's the one React concept that is *purely* about reconciliation, and it leaks through the "declarative, no manual DOM" fantasy.

### 2.5 "Nothing changes on the backend" — the load-bearing wall

F10's big realization — the *same* REST API serves F9's vanilla JS and F10's React — is not a coincidence. It's the payoff of the **API boundary as a contract** (F2's `response_model`, the standardized error shape, the stable URL scheme). If the backend had coupled to the frontend's mechanics (server-rendered HTML nodes, FastAPI returning "the exact `<div>` the vanilla JS expects"), adding React would require *backend* changes. Because the contract is "JSON with fields X, Y, Z," either frontend consumes it identically.

This is worth naming explicitly: **the frontend framework is a replacing part; the API is a stable interface.** That replaceability is what makes the "migrate vanilla → React" exercise (F9 → F10) possible at all. It's the *same* lesson as "the service depends on the cache-store *interface*, not the SQLite implementation" (F4/F5) — swap out one side, contract unchanged, other side untouched. Recognize it as the identical architectural move, one level closer to the user.

### Field notes — Feature 10

> **⚠️ React 18/19 StrictMode runs effects twice in dev.** The doc's `useEffect` fetch runs, its cleanup runs, its fetch runs again — by design (a dev-only check to catch effect bugs). Seeing doubled dev logs is not a leak. If your "fetch once" logic breaks under StrictMode (double increment of a counter, double request), that's the effect not being *idempotent* — a real signal, not a tooling quirk.

> **⚠️ `useEffect(fn, [])` + missing cleanup = the classic "state on unmounted component" error.** If a component unmounts while a fetch is in flight and you `setData` anyway, React warns (and can leak). The `alive`/cleanup pattern is the canonical fix — it's not optional polish, it's the correct behavior for "the user navigated away."

> **⚠️ Don't set state synchronously in render** (e.g. `if (x) setState(y)` inside the function body without an effect). It triggers an immediate re-render loop ("maximum update depth exceeded"). Side effects belong in `useEffect`; the render function body must stay pure (derive, don't mutate) — the same "pure function" discipline as F3's transforms, now on the frontend.

> **⚠️ Dev gives you two servers and a CORS/proxy decision.** Vite's dev server (5173) and FastAPI (8000) are *different origins*. The standard fix is a Vite `proxy` (`server.proxy['/api'] → http://localhost:8000`) so the browser only ever talks to one origin and CORS disappears in dev. Production still needs F13's real CORS config. Confusing proxy with CORS, or missing the proxy, reproduces the "works from curl, not browser" trap of F9.

> **📌 `api.js` is the frontend's **clients/** layer.** One module knowing the URL scheme, `encodeURIComponent`, `res.ok` checking — that's the "single source for how we talk to the backend," mirroring F2's `clients/github.py`. Components should never `fetch` inline (they'd each reimplement error handling). It's the same "give each responsibility one home" discipline on both sides of the wire.

## Closing note

The frontend isn't a different *kind* of programming — it's the same shape as the backend, one layer closer to the user: HTTP client ↔ server, pure-render + state ↔ pure-transform + orchestration, "one responsibility per file" ↔ the layered architecture you've been building since F3. And React's actual contribution — "describe the UI as a function of state, and the engine reconciles it" — is exactly the *pure function + dependency-injection* philosophy you've been practicing in Python, applied to the browser. Nothing here changes what you build next; but when a "magically stale count" or a "flash of wrong data" appears in a real React app, you'll be looking at reconciliation and effect timing, not confusion.
