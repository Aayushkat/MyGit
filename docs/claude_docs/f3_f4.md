## Part 1 — Feature 3: Repositories & Language Stats

### 1.1 Why "pure function" is the single most valuable idea in this feature

The doc keeps saying "make it pure." Here's the mechanism, not the slogan.

A **pure function** is one that:
- returns the same output for the same input, *always*, and
- has **no side effects** — it doesn't touch the network, the filesystem, a global variable, or the clock, and it doesn't modify its inputs.

Why is that so cheap to test and so expensive to get wrong? Because *everything it depends on is passed in as an argument and everything it produces comes back as a return value.* There is no hidden state for a test to set up and no hidden state for a bug to sneak through. `compute_portfolio(user_raw, repos_raw)` — you feed it two plain Python structures, it returns a `Portfolio`. A test can call it a thousand times in a single second, with no database, no mocking library, no server running.

Contrast: a function that reads `datetime.now()` internally is **impure** — it hides one of its inputs. That's why the f1_f2 doc told you to inject `now` into `years_active` (Feature 11's exercise). When a function reads the clock itself, the *clock* becomes input #3, and a test can't control input #3 without patching global state (`monkeypatch`). Every impurity you push out to the caller's boundary is a piece of implicit state you've made explicit.

Nothing about this is fastapi-specific. It's a general property: **impure functions are hard to test because their behavior depends on the outside world; pure functions are trivial to test because the outside world is their inputs.** This is *why* the discipline of extracting transforms into standalone functions pays off — not "because it's clean," but because it converts an integration problem into a math problem.

### 1.2 `Counter` vs `defaultdict` vs a plain dict — and why you should care about the difference

The doc offers three ways to count by language. They're not interchangeable sugar; they have subtly different contracts:

```python
# 1. Imperative
counts = {}
for repo in repos:
    counts[lang] = counts.get(lang, 0) + 1

# 2. defaultdict
counts2 = defaultdict(int)
for repo in repos:
    counts2[lang] += 1

# 3. Counter
counts3 = Counter(r["language"] for r in repos if r.get("language"))
```

Mechanically they're the same hash-table increment. Behaviorally:

- `dict.get(lang, 0)` — you wrote the "initialize on first sight" logic by hand. Fine, but it's *described in the loop*, every loop.
- `defaultdict(int)` — the default-value logic is bound to the *container*, not the loop. Cleaner, but beware: `counts2[missing_key]` **creates** the key with value 0. If you later iterate `counts2.items()` expecting only languages you saw, you'll include phantom zeros. That phantom-write also mutates the dict during a read — a real source of confusion.
- `Counter` — a subclass of dict with two extra tricks relevant here: `.most_common()` returns pairs sorted by count descending (that's your sort-for-free), and `Counter` has arithmetic (`+`, `-`) so you can combine counts from multiple pages — handy the day pagination gives you several repo lists.

The *why-you-should-care* is not which one is "better." It's that each one encodes a decision about *who owns the default behavior* (the loop, the container, or the type) and *who's allowed to create keys*. Cargo-culting `Counter` because "it's fancy" without knowing it auto-sorts (and that `most_common()` ties break by insertion order) is exactly the kind of assumption that bites later.

### 1.3 Rounding: why 33+33+33 = 99, and what "fix the rounding" actually means

`round(1/3 * 100)` is 33 for each of three equal languages. Sum: 99. Charts show a 1% hole. Two separate mechanisms are at work:

1. **Binary floating point.** `1/3` can't be represented exactly in binary (like `1/3` in decimal), so `1/3 * 100` is `33.333333333333336` or similar, and `round()` snaps it to `33`. That's compounding friction, not the real bug.

2. **Independent rounding doesn't guarantee constraints.** Each percentage is rounded **in isolation**. Rounding is a many-to-one map: many exact values land on the same integer. So nothing forces `sum(rounded) == 100`. This is a *math* error, not a floating-point quirk — even with perfect rational arithmetic, `34 + 33 + 33` is only forced if you coordinate.

The fix the exercise hints at ("largest absorbs the remainder") coordinates the rounding: compute exact values, floor them, then distribute the leftover `100 - sum` one point at a time to the largest fractions. That's a real, documented technique (largest remainder method) — the same algorithm used for allocating seats in proportional-representation elections. Knowing it has a name (not just "some trick") is the difference between reproducing it and understanding it.

### 1.4 Why the service layer *appears* in F3 and not earlier

This is the "when do I add a layer?" question, and F3 is designed to make the answer visible.

In F2, the router did `client.get_user(username)` → map to model. One call, one mapping. In F3, the router would have to: fetch user, fetch repos, aggregate languages, compute percentages, sort, cap, and assemble a nested model. That's *seven distinct concerns* in HTTP-land. The service layer exists for one mechanism: **the router should only know about HTTP; everything else is not the router's job.**

The *mechanism* to internalize is not "services are good" — it's the principle of **single responsibility applied at the seam of a dependency**. A layer is justified exactly when its *absence* would give one file two unrelated jobs. The doc calls this out, and you should be able to detect it on your own: if a route function is doing more than (a) reading the request, (b) delegating, (c) returning, it's doing too much.

Also worth noting: `ProfileService.__init__(self, client)` — the service *takes its dependency as a constructor argument*. That's **dependency injection through composition**, not through FastAPI. It means the service is testable *without FastAPI at all*: `ProfileService(client=FakeGitHub())`. This is the same pattern you'll see re-used when `session` gets added in F4. The DI system (`Depends`) wires up the *routers*; the service wires itself.

### 1.5 Sequential awaits vs `asyncio.gather` — what actually happens

The doc's service awaits user, then repos — sequentially. Here's the mechanism of why that's slower and why `gather` helps.

`await client.get_user(...)` suspends the coroutine until user data returns. Without the second call started, the *event loop* is idle for that whole first round-trip (~200-400ms). Then repos start. Total ≈ 2 × round-trip. With `asyncio.gather(*[client.get_user(u), client.get_repositories(u)])`, both httpx calls are *scheduled* before either awaits — so both sockets are in flight at the same time, and total ≈ 1 × round-trip. `gather` isn't magic: it's "start all the coroutines now (each is a task), then combine." The event loop interleaves the two waits.

The trade-off the doc mentions — error handling complexity — is real: a bare `gather` stops at the *first* exception but leaves the other task running; use `return_exceptions=True` or handle partial failures when one of the two calls can independently 404 (e.g., user exists but repos call fails). Worth feeling out in Exercise 5.

### 1.6 Pagination: the `Link` header and why GitHub delivers in pages

GitHub caps `per_page=100`. The mechanism: **responses are paginated, and the pagination lives in response headers, not the body.** The `Link` header looks like:

```
Link: <https://api.github.com/users/x/repos?page=2>; rel="next", <...page=4>; rel="last"
```

`rel` is the relationship: "next", "last", "first", "prev". A polite client reads the `next` URL from the header and keeps requesting until there is no `next`. That's the *definition of walking a paginated API* — not guessing page numbers. (You *can* guess with `?page=N`, but the header is the source of truth; GitHub may reorder or split differently than you assume.)

Two practical details: (1) don't loop forever — cap total pages (the doc says max ~200 repos), because a hostile/malformed upstream could give you an unbounded `next` chain; (2) your httpx client can read the header directly: `r.headers.get("link")`. Parsing it by hand is a classic "write it once, get it subtly wrong" task — be grateful `Link` parsing is exactly one line per rel with a regex, or use a helper.

### Field notes — Feature 3

> **⚠️ `round()` isn't "nearest to 0" — it's banker's rounding.** Python's `round(2.5)` is **2**, not 3 (round-half-to-even). For percentages that's almost always invisible, but the moment you port this code to another language (JS: `Math.round(2.5)` → 3; SQL: `ROUND` varies by engine), identical inputs give off-by-one outputs. This is a silent cross-language difference, not a Python bug.

> **⚠️ Slicing `[:5]` with fewer items** — Python slices are forgiving: `[1][:5]` is `[1]`, no error. That's *a* reason the code feels safe. But the *inverse* is where bugs hide: `.most_common(5)` on a `Counter` is a different call that also handles it — know that both exist, because `[:5]` and `.most_common(5)` are not identical when you have 0 items (both fine) vs when ties exist (`.most_common` is stable by insertion order).

> **📌 You can test the transform right now, before the router exists.** Since `compute_portfolio` is pure, `python -c "from app.services.profile import compute_portfolio; ..."` runs it with zero infrastructure. If you get in the habit of *running pure functions from a REPL or a one-liner*, you'll be doing "testing" before Feature 11 arrives.

> **📌 The `is_fork` guard is a product decision, not a math decision.** Excluding forks from language stats (Exercise 3) is choosing "language mix represents *your own* code." Keep that reasoning visible — a future teammate might "helpfully" remove the guard and silently change the product.

## Part 2 — Feature 4: Stop Hitting Rate Limits (SQLite + Persistence)

### 2.1 What a database actually is, physically

When you say `table=True`, a real file on disk gets structures that let the engine find rows fast. The mental model that explains three weird behaviors:

- **Rows live in pages inside a B-tree index.** "The table" and "the index on the primary key" are the *same* structure in SQLite — that's why primary-key lookups (`session.get`) are fast and why adding an index on `username` in F6 is "making another B-tree." A `WHERE username = ?` does a tree walk, O(log n), not a scan.
- **SQLite is a single file.** One process writes; SQLite uses an **exclusive lock during writes** (unless WAL mode). That's where "SQLite writes lock the DB" comes from — there is *one* writer at a time, by design, to keep the file consistent. Readers can be many, but a write holds the lock.
- **Postgres (F12) is a server, not a file.** It can have many writers (MVCC: readers see a snapshot, writers don't block each other). That's *precisely* why the roadmap migrates: at production scale, the single-writer file model stops scaling.

The pragmatic takeaway: **you are not "learning SQL" — you're learning what a file-based single-writer B-tree does, then learning what a server-based multi-writer database does.** Both are "a database"; the difference is concurrency model.

### 2.2 SQLModel is two libraries wearing one coat

SQLModel (by the FastAPI author) is a **merge of SQLAlchemy and Pydantic**. The `ProfileCache` class is *both*:

- a **Pydantic model** (the `model_validate`/`model_dump` you meet in 4.5 work because of this), and
- a **SQLAlchemy table** (`table=True` — SQLModel generates the `__table__` metadata + columns from the type annotations and `Field` declarations).

The mechanism of `model_validate`/`model_dump`:
- `model_dump()` walks the Pydantic model's field names and serializes them to a plain dict.
- `model_validate(data)` runs the dict through *validation* again — coercion, defaults, type checks — and returns a model instance.

That's why a cached dict (from `json.loads`) can become a `Portfolio` again with one call: Pydantic re-validates, not just re-casts. This is also the mechanism behind a subtle F4 bug: **`model_validate` will raise if your JSON has fields the model doesn't know** unless `model_config` allows `extra="ignore"`. If you cache a snapshot of an *older* schema and later deploy a model with *fewer* fields, `model_validate(cached)` throws — the first time "cache invalidation" meets "schema evolution." Worth naming now: it's a version-skew problem.

### 2.3 Engine vs Session — the actual relationship

These two get cargo-culted the hardest. The mechanism:

- **Engine** ≈ a pool of database connections, created once per app. It doesn't talk to *your* code per request; it hands out connections.
- **Session** ≈ a *transaction scope* — "one unit of work." It borrows a connection from the pool, tracks changes, commits them, and returns the connection.

The FastAPI idiom `def get_session(): with Session(engine) as session: yield session` is a **generator dependency**. The mechanism of `yield` in a dependency (flagged in f1_f2): code *before* the `yield` runs when the dependency is *entered* (per request), the `yielded session` is injected into the endpoint, and code *after* the `yield` runs when the request *ends* — including on exceptions. This is how "always close the session" is guaranteed when everything works AND when the route raises. That's the practical meaning of "teardown you can't forget."

One more real gotcha hiding in `get_session`: SQLModel's `Session` has its own `exec`/query machinery, but it's still SQLAlchemy underneath. **Don't hold a session across `await` points if you can avoid it.** The DB round-trip blocks; but a *thread* holds the connection. If you `await` something slow mid-session, you're pinning a connection open and possibly blocking another request's writer. This constraint will be *why* caching repositories in F5 keep the session out of the hot path.

### 2.4 Upsert — two operations, one trip

"Upsert" = INSERT if missing, UPDATE if present. The doc's version does it in two SQL statements (`session.get` then `add` or mutate). Databases also have a native `INSERT ... ON CONFLICT ... DO UPDATE` (SQLite/Postgres share this syntax family) — SQLModel can express it, but the two-step version is easier to read and, at this scale, fine.

Why is this more than a convenience? It's the **non-idempotent-write problem**: if you're not careful, the *same* cache row gets INSERTed twice (duplicate PK error or duplicate rows), or you burn a write for no change. The two-step form encodes the actual semantics: "refresh this cache entry or create it." Internally, SQLAlchemy tracks which objects it's seen to decide `INSERT` vs `UPDATE` on `commit`.

### 2.5 Migrations, and why `create_all` can't evolve the schema

`create_all` reads the model classes and creates *missing* tables. The key limitation: it **never alters existing tables** — it was designed for "first time you stand up a DB."

Alembic's mechanism: it maintains a special table, `alembic_version`, recording which *revision* (migration) the DB is at. `alembic revision --autogenerate` *diffs* your model metadata against the live DB schema and generates code for the delta. `alembic upgrade head` applies pending migrations in order. The win: adding the `views` column later is a **new migration that runs `ALTER TABLE ADD COLUMN` and preserves existing rows** — whereas `create_all` for a model with the new column would do *nothing* to an existing DB. That difference — "the schema is versioned, not just declared" — is the entire reason migrations exist.

> **Field note:** autogenerate is a *suggestion* engine, not a diff oracle. It misses things like column *renames* (it usually sees a drop+add instead) and it doesn't watch *data* changes. Treat `--autogenerate` output as a first draft. It must be imported into `env.py` (the migration env must see models), or it "finds nothing" — a classic silent failure.

### 2.6 Cache semantics — the "if fresh, serve" mechanism

The cache-or-fetch logic is a small **state machine with three states**: MISS (no row), HIT (row fresh), STALE (row old → treat as MISS but *still have the data*). Feature 4's code collapses STALE → MISS. Feature 5's Redis swap collapses freshness into a TTL. The important underlying concept is **cache-read policy**: freshness is measured *in the policy layer* (service), while storage is in the repository — that's why the service changes nothing when you swap storage backend in F5.

One subtlety the original doc raises (Exercise 1) is **stale-but-serve**: sometimes it's better to serve a slightly old answer than to risk a slow/failing upstream. This "stale-while-revalidate" concept — serve the stale copy immediately, fetch fresh in the background — is exactly what F5's SWR note and the reference app's KV cache are doing. Understand it *here* as a policy of "never block the user on the upstream," and F5's Redis TTL becomes a *relocation* of the same idea, not a new one.

### Field notes — Feature 4

> **⚠️ `datetime.now(timezone.utc)` vs naive datetimes.** Mixing naive (`datetime.now()`) and aware (`datetime.now(timezone.utc)`) datetimes raises `TypeError: can't compare offset-naive and offset-aware datetimes`. Your `fetched_at` must be consistently aware (UTC) **all the way**: at write, at the freshness comparison, and at serialization. This is the #1 silent datetime bug.

> **⚠️ SQLite + `check_same_thread=False` is about threading, not "allow anything."** FastAPI may serve requests from multiple threads. SQLite historically forbids a connection created in one thread from being used in another — a false "database is locked" or "wrong thread" error. The flag relaxes that safety check. It's a *pragmatic lie*, not a configuration virtue — it's precisely why production uses Postgres (per-connection thread safety, not per-file).

> **⚠️ `.env` location, again.** Same rule as Feature 2: `Settings()` reads `.env` relative to the current working directory. Two terminal tabs with different CWDs = one app sees the DB URL, the other silently defaults. If you see `sqlite:///./github_portfolio.db` created in an unexpected place, that's the sign.

> **⚠️ A session that's committed but not refreshed.** After `session.add(row); session.commit()`, the object may hold a stale/default `id` until `session.refresh(row)` re-reads it. Routers in F6 that return an object right after commit rely on refresh. Forgetting it gives you a row whose PK "is None" in the response even though the DB row exists.

> **📌 JSON-as-a-column is a *cache* decision, not a data-modeling decision.** Storing a whole portfolio as one JSON string is right for a cache (read it all back whole). The moment you need to *query within* the profile ("all repos from 2024 with >10 stars"), that storage is wrong — you'd normalize. Knowing *when each is right* is the lesson, more than the code.

> **📌 Watch the log to *feel* a cache hit**: request 1 (MISS) ~ hundreds of ms with GitHub calls; request 2 (HIT) ~ single-digit ms. If you can't distinguish them by timing, you don't have a cache — you have a slower network layer.

## Closing note

Feature 3 taught you that **computation is a pure math layer you can isolate and test without any infrastructure.** Feature 4 taught you that **a database is a concurrency model with real physical constraints — single-writer files on the small end, multi-writer servers on the big end.** Everything in F5 and beyond (Redis, rate limits, Postgres in production, background tasks, tests) is a continuation of these two mechanisms: give each concern its own layer, and make each layer's inputs explicit. Nothing here changes what you build next — but when a cache row "inexplicably succeeds while the data is a day old," or a "database is locked" error appears, you'll know exactly what machinery is telling you what.
