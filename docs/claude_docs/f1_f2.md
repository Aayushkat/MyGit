## Part 1 — Feature 1: Hello, Portfolio API

### 1.1 The stack underneath the stack

The original doc gives you three layers: uvicorn → FastAPI → your function. True, but there's a hidden fourth layer, and knowing it exists will save you real confusion the first time an error message mentions a library you never imported.

**FastAPI doesn't implement HTTP routing, middleware, or the request/response objects itself.** It's built on top of a smaller framework called **Starlette**, and adds two things on top of it: Pydantic-based validation, and automatic OpenAPI documentation. When you write:

```python
from fastapi.responses import HTMLResponse
```

...you're importing a class FastAPI didn't write — `fastapi.responses` just re-exports Starlette's `HTMLResponse`. This explains a real experience you'll have soon: a traceback that says `starlette.exceptions` or `starlette.routing` somewhere in the stack, looking like some unrelated library broke. It didn't — you're one layer further down the *same* stack you're already using.

```
uvicorn ── speaks raw HTTP over a TCP socket
   │
   ▼
Starlette ── routing, middleware, request/response objects   (FastAPI is built on this)
   │
   ▼
FastAPI ── validates input/output against your types, generates OpenAPI docs
   │
   ▼
your function
```

**What ASGI actually is**, since "ASGI application object" got used without being defined: ASGI (Asynchronous Server Gateway Interface) is a *specification* — a contract describing the exact shape a Python callable must have for a server to hand it requests. It's the async-capable successor to WSGI, the older, strictly-synchronous spec that Flask and classic Django use (one request, one blocking function call). ASGI's contract allows a function to `await` — to pause on I/O and let other requests get handled meanwhile. uvicorn is an **ASGI server**: it listens on a socket, parses raw bytes into an HTTP request, and calls into an ASGI application. Starlette (and therefore FastAPI) is an **ASGI application**: something that fulfills that calling contract. `app = FastAPI(...)` is the object satisfying it. This is also why a plain Flask app can't be run with `uvicorn app.main:app` — Flask objects are WSGI applications, and uvicorn only speaks ASGI; the calling contracts aren't compatible without an adapter in between.

> **Field note:** you'll see "ASGI app" used loosely to mean "the FastAPI instance." Technically correct — `FastAPI()` *is* an ASGI application — but so is a raw Starlette app, a websocket handler, or a Django app running in ASGI mode. "ASGI application" describes the *shape*, not the framework.

### 1.2 One event loop, cooperative multitasking — and why `--workers` will matter later

`uvicorn app.main:app --reload` starts **one process** running **one event loop**. Every request — even once async GitHub calls arrive in Feature 2 — is handled by that single loop, on a single thread. The concurrency FastAPI gives you is *interleaving*, not parallelism: while one request waits on I/O, the loop makes progress on a different request. Nothing runs on two CPU cores at once.

This matters for something you'll do soon: **any in-memory state you add (a cache, a counter) lives inside that one process.** The moment you deploy with multiple workers for real traffic —

```bash
uvicorn app.main:app --workers 4
```

— you get 4 separate Python processes, each with its own event loop and its **own memory**. A `dict` used as a cache in worker 1 is invisible to worker 2; two users hitting different workers can get inconsistent answers from what looks like "the same cache." That's exactly the trap waiting in Feature 4 once in-memory caching shows up — worth filing away now so it isn't a surprise later. (The fix at that point is an external, shared store — Redis — precisely *because* it lives outside any one worker's memory.)

It's also the concrete reason `--reload` is dev-only, beyond "it's convenient": reload watches your filesystem and restarts the *entire process* on save, which only makes sense for a single worker you're actively editing.

### 1.3 Decorators, route-matching order, and the trailing slash

`@app.get("/hello")` is a **decorator factory**: `app.get("/hello")` runs first and returns a decorator, which is then applied to `hello` — equivalent to `hello = app.get("/hello")(hello)`. Nothing magic, just a function that registers yours into the app's internal route table.

That "route table" detail matters more than it looks: **Starlette matches routes in registration order, first match wins.** Invisible right now with only static paths — it stops being invisible the moment a path parameter sits alongside a fixed path with the same prefix, which, given where this project is headed (an authenticated `/users/me` next to the already-planned `/users/{username}`), you likely *will* do soon. Register `/users/{username}` before `/users/me`, and a request to `/users/me` matches the dynamic route first — your handler receives `username="me"` and never reaches the `/me` route. Fix: **register specific/static paths before dynamic ones.** This is one of the most common real-world FastAPI bugs, and it produces no error at all — just a request quietly going to the wrong handler.

One more routing behavior worth knowing before it confuses you: Starlette's default is `redirect_slashes=True`. Define `GET /hello`, and a request to `/hello/` (trailing slash) doesn't 404 — it gets a `307 Temporary Redirect` back to `/hello`. Browsers and `curl` follow redirects transparently, so you won't notice there. Some `fetch()` configurations don't, and you'll see a request that "just doesn't return the JSON you expected," with no obvious error — it silently got a redirect instead of your data. Worth remembering once Feature 9's frontend starts making its own requests.

### 1.4 `main.py`, the import string, and package mechanics — one level deeper

`uvicorn app.main:app` splits on the colon and does, roughly, `getattr(importlib.import_module("app.main"), "app")`. Two consequences:

1. **`app` must be a module-level name.** If you ever refactor toward an "app factory" pattern (`def create_app(): ... return app`) — a real, common pattern in larger projects — plain `uvicorn app.main:app` won't find it, because there's no module-level `app` to grab; you'd need `uvicorn app.main:create_app --factory`. Not needed now, but the resulting error (`AttributeError: module 'app.main' has no attribute 'app'`) is confusing if you don't know why.
2. **`app/__init__.py` isn't strictly required by modern Python** — since 3.3, a folder without `__init__.py` can work as an "implicit namespace package." The doc has you create an empty one anyway, and that's the right call: explicit packages behave more predictably across tooling (pytest's rootdir detection, some import-resolution edge cases in editors/type-checkers) than namespace packages do. A small, deliberate choice for fewer surprises later — not boilerplate for its own sake.

### Field notes — Feature 1

> **⚠️ PowerShell blocks venv activation on a fresh Windows machine.** Running `.venv\Scripts\Activate.ps1` for the first time on a machine that's never had a script-execution policy set can fail with *"cannot be loaded because running scripts is disabled on this system."* One-time fix, in that same window: `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`, then re-run activate. Specific to PowerShell — `cmd.exe`'s `.venv\Scripts\activate.bat` doesn't have this restriction.

> **⚠️ "Address already in use."** `--reload`'s file-watcher occasionally leaves a child process alive after `Ctrl+C`, or you start a second uvicorn on the same port by accident. Find what's holding port 8000 with `lsof -i :8000` (macOS/Linux) or `netstat -ano | findstr :8000` (Windows), then kill that PID — or sidestep it for a quick test with `--port 8001`.

> **⚠️ `pip install` "succeeds" but `uvicorn` isn't found, or imports fail.** Almost always means the venv isn't actually active in the shell you're running from — a fresh editor-integrated terminal, or a machine with two Python installs where `pip` and `python` silently resolve to different ones. Check with `python -m pip show fastapi` and compare against `which python` (macOS/Linux) / `where python` (Windows) — if it's not inside `.venv`, that's the whole bug.

> **⚠️ A route can return `None` and you'll get a "successful" empty response, no error.** Nothing forces every code path to hit a `return {...}`. If one branch falls through, FastAPI serializes `None` and sends `200 OK` with body `null` — no exception, no warning. Worth remembering once your routes grow an `if/else`.

> **📌 `/openapi.json` is the actual contract — `/docs` and `/redoc` are two UIs rendering the same file.** Once you know that URL exists, tools like Postman ("Import → Link") or an OpenAPI code generator can consume your API's exact shape without you writing a client by hand. Useful the moment Feature 9's frontend needs to know precisely what your endpoints return.

## Part 2 — Feature 2: GitHub Profile Search

### 2.1 async/await: what it actually buys you, and the one rule that matters

`async def` marks a function as a **coroutine** — one that can pause. `await` is the pause point: *"suspend here, let the event loop do other work, resume me when this specific thing finishes."* To your eyes the code reads top-to-bottom like normal sequential code; underneath, the loop juggles many paused-and-resumed functions at once.

The one rule that matters more than the mechanics: **async speeds up waiting, not computing.** It helps exactly when a function is idle because it's waiting on something external — network, disk, another process. It does nothing for CPU-bound work — hashing a password, resizing an image, hand-parsing a huge JSON blob. An `async def` function doing heavy computation instead of awaiting I/O still blocks the *entire* event loop for its whole duration, exactly like a sync function would — except now it blocks every other concurrent user too, not just its own caller. You won't hit this with GitHub calls (pure I/O waiting), but it's worth planting now — it becomes very relevant the day password hashing or local file/image processing shows up.

This also answers something the two docs never explicitly connect: **why does Feature 1 use plain `def` and Feature 2 use `async def`?** FastAPI supports both and treats them differently under the hood. An `async def` route runs directly on the event loop. A plain `def` route is automatically dispatched to an external **threadpool** (via Starlette/AnyIO) so a slow synchronous function doesn't block everyone else — a safety net, not a scaling strategy, and that threadpool has a real, limited size (AnyIO's default worker-thread limiter caps out around 40 concurrent threads). The practical rule from here on: **any route or function doing network/DB I/O should be `async def`, paired with an async-capable library** — httpx here, not `requests`; later, an async database driver, not a sync one. Actively avoid calling a *blocking* library from inside `async def` — that freezes the single event loop for every concurrent user, not just the one who triggered it, and it's one of the easiest ways to make an "async" app perform *worse* than a plain sync one under load.

One near-silent bug worth knowing about before meeting it live: **forgetting `await` doesn't raise an exception.** You get a `RuntimeWarning: coroutine 'x' was never awaited` printed to the console — easy to miss in a wall of dev-server output — and the call you thought you made simply never executes.

### 2.2 The `httpx.AsyncClient` lifecycle — and a real anti-pattern sitting in Piece 3

This is the single most valuable "only learned by hitting it" item in Feature 2, worth slowing down for.

`httpx.AsyncClient()` isn't just a way to make one request — it owns a **connection pool**. The first time it talks to `api.github.com`, it pays a TCP handshake and (since it's HTTPS) a TLS handshake. Reuse the *same* client for the next request to the same host, and httpx keeps that connection warm (keep-alive), skipping the handshake entirely. That reuse is the entire point of the class existing as a long-lived object instead of a one-shot function.

Now look at Piece 3 again:

```python
async def get_user(self, username: str) -> dict:
    async with httpx.AsyncClient(headers=self._headers, timeout=15.0) as client:
        r = await client.get(f"{self.BASE}/users/{username}")
    ...
```

A brand-new `AsyncClient` — a brand-new, empty connection pool — is created and torn down on **every single call**. At tutorial scale (you, alone, hitting `/users/torvalds` a few times) this is invisible; each request quietly re-pays the handshake cost, and 15–30ms of extra latency on a request already dominated by GitHub's own response time doesn't register. Under real traffic it does: every request pays a fresh handshake instead of reusing a warm connection, showing up in a load test or profiler as measurably higher latency and CPU spent on TLS — never as an error, just as "this is slower than it should be," which is a much harder kind of problem to notice than a crash.

**The senior fix: create one `AsyncClient` when the app starts, reuse it for every request, close it on shutdown.** FastAPI's mechanism for exactly this is a `lifespan` context manager:

```python
# app/main.py
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI
from app.routers import github, hello

@asynccontextmanager
async def lifespan(app: FastAPI):
    # runs once, before the app starts accepting requests
    app.state.http_client = httpx.AsyncClient(timeout=15.0)
    yield
    # runs once, on shutdown
    await app.state.http_client.aclose()

app = FastAPI(title="GitHub Portfolio", lifespan=lifespan)
app.include_router(github.router)
app.include_router(hello.router)
```

```python
# app/clients/github.py
import httpx
from app.config import settings

class GitHubClient:
    BASE = "https://api.github.com"

    def __init__(self, http_client: httpx.AsyncClient):
        self._client = http_client
        self._headers = {
            "Accept": "application/vnd.github+json",
            "User-Agent": "github-portfolio-app",
        }
        if settings.github_token:
            self._headers["Authorization"] = f"Bearer {settings.github_token}"

    async def get_user(self, username: str) -> dict:
        r = await self._client.get(f"{self.BASE}/users/{username}", headers=self._headers)
        # status-code handling (404 / 403 / 429 / raise_for_status) stays exactly
        # as in Piece 3 — only where the client itself comes from has changed
        ...
```

```python
# app/routers/github.py — only the dependency function changes
from fastapi import Request

def get_client(request: Request) -> GitHubClient:
    return GitHubClient(request.app.state.http_client)
```

Everything downstream (the route function, the `Depends`) stays exactly the same shape — only *what gets constructed* changes, from "a throwaway client" to "a handle onto the one shared client." Worth recognizing on its own: fixing a real performance problem here doesn't require rewriting the architecture, just relocating where an object's lifetime lives.

One more layer of granularity worth knowing for later: `timeout=15.0` applies that same 15 seconds to *connect*, *read*, *write*, and getting a connection from the *pool*, all at once — a bare float sets all four. In production you'd usually split them: `httpx.Timeout(connect=5.0, read=10.0, write=5.0, pool=5.0)`, because a connection that never opens (DNS failure, network unreachable) is a very different failure than a connection that opens fine but GitHub is just slow to respond — you may want to react to those differently (fail fast on the former, retry on the latter).

### 2.3 Pydantic `response_model` as a contract — and the bug sitting in Piece 4

`response_model` is a contract, but it's worth being explicit about *why* it's also a safety net: it's an active **filter**, not just documentation. Even if the dict you're working with has ten fields, only the ones declared on the model make it into the response. You cannot accidentally leak a field that isn't declared — including, later, something like a raw internal ID you didn't mean to expose. That's a real security property, not just tidiness.

Now walk Piece 2 and Piece 4 side by side:

```python
# schema (Piece 2)
class GitHubUser(BaseModel):
    login: str
    ...

# router (Piece 4)
return GitHubUser(username=data["login"], name=data.get("name"), ...)
```

The model's field is `login`. The router constructs it with `username=`. Typed exactly as written, this doesn't fail quietly — it throws, loudly, the first time that line runs:

```
pydantic_core._pydantic_core.ValidationError: 1 validation error for GitHubUser
login
  Field required [type=missing, input_value={'username': 'torvalds', ...}, input_type=dict]
```

Worth hitting this on purpose once, because it teaches you to read a Pydantic validation error: it names exactly which field (`login`) is missing and what input it actually got (a dict with `username` in it instead) — everything needed to spot the mismatch is right there, once you know to read past the first line. The fix is matching the names: `GitHubUser(login=data["login"], ...)`. The deeper lesson is the one Feature 2's own Exercise 3 is quietly pointing at: **manually re-typing field names when constructing a model from a dict is duplication that silently rots.** Python has no compiler to catch "the schema changed but the manual construction didn't" ahead of time — you find out at runtime, exactly like this. A `GitHubUser.from_raw(data)` classmethod puts the mapping in one place, next to the model it belongs to, so it can't drift out of sync again.

Smaller, related note: the doc writes `username: str = Path(..., min_length=1, ...)`. FastAPI's own docs now lead with a different style for this — `username: Annotated[str, Path(min_length=1, max_length=39, pattern=r"^[a-zA-Z0-9-]+$")]`. Both work today. `Annotated` exists because the old style ties a parameter's *type* and its *validation metadata* together through a default value, which forces every "has a default" parameter (`= Path(...)`, `= Depends(...)`) to come after every parameter that doesn't — a real ordering headache once a route collects more than one or two params. Not worth changing today; worth recognizing when it shows up in FastAPI's own examples so it doesn't look like unrelated, unfamiliar syntax.

### 2.4 Dependency injection, one layer deeper

`Depends(get_client)` is resolved **fresh, per request, by default** — right now that means every request builds a brand-new `GitHubClient()`. Harmless currently, since the object holds nothing but a headers dict. But notice what this means once 2.2's fix is in place: the dependency function's job changes from *"construct a new thing"* to *"hand out the one shared thing living on `app.state`"* — shown in the `get_client(request: Request)` version above. FastAPI's DI system doesn't decide an object's lifetime for you; *you* decide it, by choosing what the dependency function does. "Build fresh every time" and "hand out a singleton" are both completely normal — the client-holding-a-connection-pool case above is exactly the kind of dependency where a singleton is the right call.

One more shape worth being able to recognize when you meet it (not needed yet): dependencies can use `yield` instead of `return` — code before the `yield` is setup, code after is teardown, guaranteed to run even if the route raises. That's the pattern a database session will use in a later feature (open session → yield it → close session, even on error) — filing the name now so it's recognizable rather than mysterious then.

### 2.5 Why Step 9's refactor isn't just style

Worth being explicit about *why* Step 9 moves error-handling out of the client, because "it's cleaner" undersells the real reason. Piece 3's client raises `HTTPException` directly — a Starlette/FastAPI-specific class. That quietly gives `GitHubClient` (conceptually: *"a thing that fetches GitHub data,"* nothing about web servers) a hidden dependency on a web framework. Two concrete costs:

1. You can't reuse `GitHubClient` outside an HTTP request — a one-off script, a scheduled background job, a REPL session — without dragging in a class (`HTTPException`) that does nothing useful there; there's no HTTP response for it to attach to.
2. In Feature 11, testing the client in isolation implicitly tests FastAPI's exception machinery too, blurring what the test actually checks.

Step 9's fix — a plain Python exception (`GitHubError`) raised by the client, with the "how does this become an HTTP response" decision handled once, at the boundary, via `@app.exception_handler` — is a specific case of a general pattern worth naming: **push framework-specific types to the outermost layer; keep inner layers (clients, business logic) framework-agnostic.** The client should be able to say "GitHub said no, and here's why" without knowing or caring that the caller happens to be a web request.

One bonus mechanic worth knowing once the error zoo grows past one type: Starlette resolves exception handlers by walking the raised exception's class hierarchy (`__mro__`), not just matching the exact type. A later feature introducing `class DatabaseError(AppError)` and `class AuthError(AppError)` alongside `GitHubError(AppError)` can register **one** handler for the shared base `AppError` and have it catch all three — no separate handler per error type needed.

### 2.6 The GitHub API's actual behavior (worth knowing precisely)

A couple of these update GitHub's current guidance slightly past what the doc uses — nothing here breaks the existing code, it's just worth having exactly right rather than approximately right.

| | What the doc uses | Current GitHub guidance |
|---|---|---|
| Accept header | `application/vnd.github.v3+json` | `application/vnd.github+json`, with the API version pinned separately via an `X-GitHub-Api-Version` header (currently `2022-11-28`). The `v3+json` form still works — GitHub keeps it for backward compatibility — but new code should use the pair above. |
| Auth header | `Authorization: token {token}` | Still valid for classic personal access tokens. `Authorization: Bearer {token}` is the form GitHub's current docs lead with throughout, and it's *required* — not just preferred — if you're ever passing a JWT instead of a PAT. Worth defaulting to `Bearer` now so there's nothing to remember to switch later. |

**Rate limits, precisely:** unauthenticated requests get **60/hour**, tracked per *source IP* — not per user, which is a real gotcha if you're testing from a shared IP, a university network, or certain cloud CI runners, where that quota might already be partly spent by someone else before you make a single request of your own. An authenticated request with a personal token gets **5,000/hour**. Every response — not just failures — carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (a Unix timestamp), so a robust client checks `X-RateLimit-Remaining` proactively instead of waiting to be told no.

**The genuinely non-obvious part: a `403` is not automatically "you hit your rate limit."** GitHub distinguishes a **primary** rate limit (your hourly quota — `X-RateLimit-Remaining` hits `0`) from a **secondary** rate limit (an abuse-prevention trigger: too many concurrent requests, too many requests to one endpoint per minute, too much compute time) — and secondary-limit responses can arrive as a 403 *while `X-RateLimit-Remaining` is still well above zero*. Treating every 403 as "back off until `X-RateLimit-Reset`" is subtly wrong for the secondary case; the correct signal there is the `Retry-After` header when present, or exponential backoff if it isn't. Piece 3's current handling (`403 or 429` → one generic 429) is a completely reasonable simplification for where the project is right now — worth knowing it *is* a simplification, so the distinction isn't a surprise when Feature 4 gets serious about resilience.

**One more thing worth banking for Feature 4 (caching):** GitHub supports **conditional requests** — send back the `ETag` a previous response gave you via an `If-None-Match` header, and if nothing changed, GitHub returns `304 Not Modified` with an empty body — and that 304 **doesn't count against your rate limit**. A free way to check "did anything change?" without spending quota, and exactly the mechanism a cache-aside layer will want later.

### 2.7 One more thing worth knowing about usernames

GitHub usernames are case-insensitive for lookup — `torvalds`, `Torvalds`, and `TORVALDS` all resolve to the same account — but the API always returns the account's canonically-cased `login` in the response body. Nothing breaks today because of this. It becomes relevant the moment Feature 4 adds caching: cache by whatever string the user typed, and two different-cased requests for the same person produce two different cache keys pointing at identical data — a quiet waste, not a bug you'd notice by testing. The fix, when you get there, is to normalize (lowercase) before using a username as a cache key — or better, cache under the canonical `login` GitHub hands back.

### 2.8 `raise_for_status()`, and two things that look like bugs but aren't

httpx's `.raise_for_status()` raises `httpx.HTTPStatusError` — a **different exception family** from FastAPI's `HTTPException`. Right now Piece 3 only reaches it for status codes it didn't explicitly branch on (a GitHub-side 500, for instance). If that's ever triggered and nothing catches it, it propagates unhandled, and FastAPI's default behavior turns it into a generic `500 Internal Server Error` with no useful detail in the response body (the real traceback lands in your own console — fine in dev, a real information leak if it ever reached a client in prod unchanged). Once Step 9's exception-handler pattern exists, this is exactly the class of failure worth wrapping the same way: catch `httpx.HTTPStatusError` / `httpx.RequestError` around the client call and re-raise as your own `GitHubError`, so *every* failure mode produces the same shaped error — not just the two GitHub explicitly told you about.

And a reassurance, since it can look wrong the first time you stare at it: using `r.status_code` or `r.json()` **after** the `async with httpx.AsyncClient(...) as client:` block has closed is *not* a bug. A regular (non-streaming) `client.get()` fully reads the response body into memory before returning, so `r` stays completely usable even once the client itself has shut down. That's different from `client.stream()`, which requires reading the body *while still inside* the `with` block — a distinction worth having in your head before reaching for streaming responses in a later feature.

### Field notes — Feature 2

> **⚠️ The bug above, concretely.** `GitHubUser(username=data["login"], ...)` will crash with a Pydantic `ValidationError` on the very first real request — see §2.3 for the exact traceback and fix.

> **⚠️ `.env` resolves relative to your *current working directory*, not to `config.py`'s location.** Run uvicorn from anywhere other than the project root — a different terminal tab, a Docker `WORKDIR` that doesn't line up, an IDE run-configuration with its own CWD — and `Settings()` won't error. It'll just quietly fall back to `github_token=None`. You'll see the app behave as if you're unauthenticated (60 req/hr, no obvious error) and can easily spend a while suspecting the *token itself* is wrong before realizing the file was never found.

> **⚠️ The search form on `/` won't reach `/users/{username}` yet — and that's expected, not something to debug.** `<form action="/users/" method="get">` with an input named `q` submits as `/users/?q=torvalds` — a **query string**. The route is a **path parameter**, `/users/{username}`, which needs the value *inside* the path (`/users/torvalds`), not after a `?`. Query params and path params both "carry a value," but they're not interchangeable — that mismatch is exactly why the doc calls this a placeholder and defers real search UX to the frontend feature.

> **⚠️ A `403` from GitHub is not automatically "you're rate limited."** See §2.6 — it can be the secondary (abuse-prevention) limit instead, which behaves differently and isn't fixed by waiting until `X-RateLimit-Reset`.

> **⚠️ Forgetting `await` doesn't crash — it warns, quietly.** A `RuntimeWarning: coroutine '...' was never awaited` printed to the console is easy to miss in a busy dev-server log, and the call you thought you made never actually ran.

## Closing note

Nothing here changes what you build next — Feature 3 still starts exactly where the original doc leaves off. What changes is what a bug report or a slow-under-load app will *mean* to you once you hit it: a 403 that isn't a simple rate limit, a cache that's about to behave differently across two workers, a `ValidationError` you can now read in three seconds instead of thirty minutes. A lot of this — the shared `AsyncClient`, the `X-RateLimit-*` headers, the `ETag`/`304` trick — is explicitly setup for Feature 4 (caching, rate-limit handling) and Feature 11 (testing); you're not doing extra work now so much as noticing the seams the curriculum already planned around.
