# Feature 11 & 12 — Extended Theory & Field Notes

> **What this is:** the layer underneath F11 (pytest + TestClient) and F12 (Docker, compose, CI). Read it after you've built both features once.

## Part 1 — Feature 11: Testing (pytest + TestClient)

### 1.1 What a test *is*, mechanically

A test is a small program that: (1) sets up a state, (2) performs one action, (3) asserts an observable outcome. That's literally all `pytest` adds on top of `assert`: `assert` *is* the test. `pytest`'s contribution is *not* a testing metalanguage — it's:

- **collecting** files matching `test_*.py` and functions named `test_*`,
- running them, isolating failures, and summarizing,
- a **fixture** system and **parametrization** (bread-and-butter tools, not magic),
- assertion *introspection* ("`assert langs["Python"] == 67`" prints the actual values on failure — invaluable).

The mechanism of the doc's title "test everything": **each test is a hypothesis about the code ("this endpoint returns 200 with this shape") plus a check.** The more of those you write, the more *behavioral contract* you lock in — and the more a future change that breaks behavior produces a *failure with a name*, instead of a production incident. Test count is not the goal; **"if this refactor silently changed behavior, does a test that catches it exist?"** is the goal.

### 1.2 `TestClient` — how it "runs the app without a server"

The trick the doc casually drops ("no socket, no port") is the actual mechanism:

`TestClient(app)` does **not** start uvicorn, bind a port, or listen on localhost. It calls the ASGI application *directly, in-process*, via an adapter (Starlette uses `httpx`'s **ASGITransport**): it constructs a *request object* (URL, method, headers, body), hands it to `app`, and the app runs its full middleware → routing → dependency → view → response pipeline, returning a real response object. No TCP, no network stack, no real sockets involved at any point.

Why that matters (the "payoff of the seam" from F2/F5): an *in-process* call is fast, deterministic, and trivially controllable. `TestClient` gets *all* of your code to run — middleware, dependencies, `response_model`, exception handlers — except the real external boundary (GitHub). Which is exactly where F11's fake comes in: the test wants "everything of ours, nothing of theirs."

### 1.3 Fake vs stub vs mock — what the doc's `FakeGitHub` is

These get used interchangeably and the difference is pedagogical gold:

- **Stub** — returns a fixed, canned answer. `fake.get_user(u)` always returns `{"login": u, ...}`. *Used for: providing an answer.*
- **Fake** — has working (often simplified) *behavior*, not just canned returns. `FakeGitHub` that actually raises `404` when `username == "missing"` is a **fake**: it encodes *behavior*, so the `404` error path is really exercised through the routing/exception-handler code.
- **Mock** — records *calls* and lets you *assert on interactions* ("`get_user` was called with `'torvalds'`", exactly once). *Used for: verifying behavior.* `unittest.mock.Mock` and the poll-style `monkeypatch` are mocks.

The doc's choice — a **fake with behavior**, injected via `dependency_overrides` — is the professional sweet spot because it tests *your logic* ("does my service translate a 404 into the right error?") rather than merely "does it return what I canned." A pure stub would never exercise your error handling; a mock would couple the test to your call structure, making refactors noisy. The fake gives you *behavior of the outside boundary, fully under your control*.

### 1.4 `dependency_overrides` — the seam, mechanically

F2 installed DI ("router declares `Depends(get_client)`; FastAPI builds it"). F11 cashes it in:

```python
app.dependency_overrides[get_service] = lambda **kw: ProfileService(client=FakeGitHub(), session=None)
```

The mechanism: FastAPI keeps a dict `app.dependency_overrides` that maps *dependency function → replacement function*. When FastAPI resolves a dependency and finds its callable in that dict, it calls the *replacement* instead. So the router's `service: ProfileService = Depends(get_service)` resolves to your lambda; the rest of the pipeline (routing, `response_model`, exception handlers) is untouched. You've told the framework "for `get_service`, don't build the real one — build this fake-fed one."

Why this beats patching `httpx` (e.g. `respx`/`responses`)? Because the seam is at **your** boundary (`GitHubClient`), not the library's. `respx` mocks *httpx's internals everywhere* — it doesn't run through your `GitHubClient`'s error-mapping at all, so a refactor of the client breaks such tests *though the behavior is unchanged*. Overriding *your own* seam tests *your* code and stays robust to library changes. That's the entire argument for putting a seam (a `clients/` layer) in the codebase in the first place.

### 1.5 TDD — red, green, refactor, *because* of the mechanism

F11's "write the test first" isn't ritual — it's the mechanism of design-by-contract:

1. **Red:** you write a test describing a behavior that *doesn't exist* yet. Running it fails. The failure message tells you what's missing (the `assert` names it).
2. **Green:** you write the minimal code to make it pass.
3. **Refactor:** you improve the code, *re-running the same test* to confirm behavior stayed put.

The *why* of test-first, mechanically: it forces you to think as *the consumer* of the API first ("what should this *do*?"), it gives every line of your new code a guard, and it prevents "the test was written to fit whatever the code accidentally does." The doc's "watch it fail, watch it pass" is precisely "the test is a hypothesis — first disprove it, then prove it." Five minutes, once, makes the whole loop *feel* real instead of cargo-culted.

### Field notes — Feature 11

> **⚠️ `dependency_overrides` are global state on `app` — clean them up.** If one test overrides `get_service` and another doesn't, and you forget to `app.dependency_overrides.clear()` in a fixture/finally block, a later test silently runs against the *previous* test's fake. It's a real, confusing, ordering-dependent failure. (The doc's fixture does `yield` then `.clear()` — that's the teardown mechanism, and it's non-negotiable.)

> **⚠️ Tests must not touch the real `.env`/`.db`/network.** Running your unit tests against the real `github_portfolio.db` or the real GitHub API makes the suite order-dependent and flaky (rate limits!). The seams exist so you *don't* have to — if you're reaching for "make the test not hit the URL," you want an override or an in-memory engine (`sqlite:///:memory:`) for DB tests, not "hope no one clicks the button during the run."

> **⚠️ `TestClient` as a context manager runs lifespan.** `with TestClient(app) as client:` runs startup/shutdown events (F2's lifespan, Redis/DB setup). A bare `TestClient(app)` may not — meaning lifespan-based setup (like an httpx client stored on `app.state`) isn't available. If "lifespan-dependent code worked in dev, fails in tests," this is usually why.

> **⚠️ Ordering and shared state between tests.** Tests in different files run in *arbitrary order*. Any test that assumes "the DB is empty" or "the counter is 0" is a lawsuit waiting to happen. Use function-scoped fixtures that create/teardown their own state per test — the F11 "in-memory engine fixture" is that mechanism.

> **📌 Parametrization is the free win.** `@pytest.mark.parametrize("path,expected", [("/x", 404), ("/../", 422)])` converts five copy-pasted tests into one table. It's the pytest feature that makes "test all the error branches" cost ~nothing extra to write — and the doc's "parametrize the error contract" exercise is exactly this.

## Part 2 — Feature 12: Docker, Compose & CI

### 2.1 What a container *is* (and the magic that isn't)

A container feels like a tiny VM, but it isn't one — no virtualized hardware, no separate kernel. The mechanism:

- **Namespaces** — Linux kernel feature that gives a process its *own view* of the system: its own process tree (PID namespace), network stack (NET namespace), filesystem root (MOUNT), users (USER), etc. From inside, it *looks* like a fresh machine; from the host's perspective, it's just a process running under restrictive namespaces.
- **cgroups** — kernel feature limiting *resource usage* (CPU, memory, IO).
- **Overlay filesystem** — how "images" are stored: a stack of **read-only layers** (one per `RUN`/`COPY`), overlaid to appear as one filesystem.

So "container" = "a process + namespaces + cgroups + an overlaid filesystem", and "image" = "the frozen, layered filesystem + metadata describing how to start it." This is *why* an image is portable and why **rebuilding is layer-cached**: Docker caches each layer, and a changed `COPY`/`RUN` invalidates only that layer and everything above it -> put the *stable* instructions (base, deps) first and the *changing* ones (your source) last, to maximize cache hits. That ordering isn't style — it's cache-awareness of the overlay mechanism.

### 2.2 The `Dockerfile` as a build manifest

Each instruction contributes a layer. Reading the F12 Dockerfile mechanically:

- `FROM python:3.12-slim` — base image (the OS + Python + a tree).
- `COPY`/`RUN` — add source and install deps, each producing a layer.
- `USER appuser` — a **security decision at the kernel level**: even if your app is compromised and escapes the process, it runs as a *non-root* user, so it can't write to the host the way root could. (Also: containers shouldn't run as root ever, not just for politeness.)
- `EXPOSE 8000` — **documentation only, not a firewall rule.** It says "the app listens on 8000," but the *host* can't reach the port unless a `-p 8000:8000` publish (from `run`/compose) maps it. The `CMD` is the process that runs when the container starts — the same `uvicorn app.main:app` you've been typing.

Understanding this matters because almost every deploy-time error is one of: (a) the image doesn't contain the file you think it does (forgot `COPY`), (b) the port wasn't published, (c) the `CMD` path doesn't match the image layout (`WORKDIR`). Those are all *read the Dockerfile top-to-bottom as a build recipe* skills.

### 2.3 Compose networking — why `db` works but `localhost` doesn't

`docker compose up` creates a **user-defined bridge network**. The mechanism: each service container gets a DNS name **equal to its service name** on that network. So inside the `api` container, `redis` and `db` *resolve*; `redis://redis:6379/0` and `postgresql+psycopg://...@db:5432/portfolio` are then real network addresses. `localhost` wouldn't work because inside the `api` container, `localhost` is *the api container itself* — there's no server listening there.

Three linked implications (each a classic field failure):

- **The F4 config swap pays rent.** Because the app reads `DATABASE_URL` from config, the whole "SQLite dev → Postgres compose/composed" change is *just a config string*. No code change. Deliberate layering = a one-line environment diff.
- **Ports are only for the outside.** `ports: ["8000:8000"]` publishes the API to the host so *you* can reach it; `db`/`redis` are *internal-only* (no publish) because the api reaches them by name. Publishing DB/Redis ports to the host is a security smell (exposing internals).
- **`depends_on` is a start-order hint, not a liveness check.** It waits until the container *is started*, not until Postgres *accepts connections* — the API can still briefly fail to connect. The fix (migrate service, healthchecks, wait-for scripts) is exactly the F12 `migrate` service pattern: a separate service that runs `alembic upgrade head` and exits, started before `api` serves traffic.

### 2.4 CI — a machine that checks your push before it's "yours"

"GitHub Actions" is a hosted runner: when a push lands, GitHub spins up a **fresh, disposable virtual machine**, checks out your code, and runs the jobs in your workflow file. The mechanism to internalize:

- **Every run starts from a clean slate.** No local venv, no installed packages, no cached `.env`. That's the *point*: CI reproduces "does this repo, on a bare machine, pass?" — catching exactly the "works on my machine" class of bug. Your reproducibility starts with being *honest* in the workflow (empty OS + `pip install -e ".[dev]"` from scratch).
- **Services (`postgres:`, `redis:`) in the workflow are containers** launched on the runner's network so your tests can connect to them by localhost — reproducing the compose environment in CI cheaply, without installing Postgres/Redis on the host.
- **A red pipeline is a gate, not a notification.** The whole *mechanism* runs *before* a merge is considered valid — which is what turns "we wrote tests" into "we *must* keep them passing." The F12 exercise "push a deliberately failing test, watch CI go red" is the mechanism made visceral.

### Field notes — Feature 12

> **⚠️ File paths in `Dockerfile` are inside the *container* (relative to `WORKDIR`), not on your machine.** A missing `COPY static/ ./static/` or a `CMD` referencing `app.main` from the wrong `WORKDIR` gives "file not found"/`ModuleNotFound` at runtime even though your *local* run works. When a container fails at a step that worked in dev, debug the *image's* layout, not your local tree.

> **⚠️ `docker-compose.yml` env interpolation + real `.env`.** `${POSTGRES_PASSWORD}` is compose reading the *host* `.env`/environment. Missing it = empty password, and sometimes a *silently created* meaningful DB. Careful: `env_file: .env` passes a file into the container; `$VAR` in the YAML reads compose's own environment. They're two different mechanisms and both are easy to confuse.

> **⚠️ Dev containers vs prod containers are the *same* image, different env.** Your F12 image ships code + Python; the `.env` (secrets) is *injected at runtime*, not baked in. Baking a real token into an image layer is semi-permanent (layers get cached and pushed far) — one more reason secrets never live in the image. The `dockerignore` stopping `.env` is enforcing *that*.

> **⚠️ Don't run SQLite in the container if you want durability.** A container's writable layer is ephemeral and *additive* (not volume-backed by default) — SQLite in that layer survives rebuilds *sometimes* but is lost when the container is recreated. That's the real push to Postgres-in-prod, not just "Postgres is fashionable."

> **📌 `docker inspect` and `docker logs` are your two F12 debug heads.** `docker inspect <c>` shows the actual state/config; `docker logs <c>` shows the app's stdout (your `print`s). When compose "works" but the stack errors, read logs *in the order the services start* — the `api` connecting before `db` is ready is the classic sequence.

> **📌 Healthchecks > `depends_on`.** Adding a `HEALTHCHECK` (or a probe) to `api`/`db` tells the runtime "wait until you've confirmed readiness," converting race-prone start-order into real readiness. F13's `/healthz` + compose healthcheck is the sanctioned upgrade — that's the mechanism *behind* the F12 exercise you're doing.

## Closing note

F11's lesson is that **your architecture's seams decide how testable the app is** — the `clients/` layer, the constructor-injected service, and the dependency-override dict are the *same* deliberate boundary, just seen from the test direction. F12's lesson is that **containers and CI are reproducibility mechanisms**: the image freezes the environment, and the fresh CI machine tests the honest claim "a bare machine can run this." Both features are, under the surface, about *trust*: tests let you trust a change; containers let you trust an environment; CI lets you trust a merge. And every time one fights you — a flaky test, a "works on my machine," a red pipeline on a passing local run — you're seeing one of these mechanisms enforcing *its* contract. Lean in: those are the best teaching failures in the whole project.
