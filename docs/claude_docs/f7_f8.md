## Part 1 — Feature 7: URL State, Counters & Background Tasks

### 1.1 Why "the URL is the app state" is a *mechanism*, not a slogan

The reference app's whole UX — `/{username}?template=bento` — is built on one fact: **HTTP is stateless, so anything the server needs to re-render a view must arrive *with* the request.** A URL is exactly that: a full, self-contained description of the view, carried in the request line itself. No session, no cookie, no DB lookup needed to know "which portfolio + which template."

Mechanically, query parameters (`?template=bento`) and path parameters (`/p/octocat`) are *both* part of the URL, and both get to the server in the request line. The design question is *which one carries what*:

- **Path** = "which resource" (`/p/{username}`).
- **Query** = "how should it be presented" (`template=`, `theme=`).

Why does this classification matter? Because caches (browser caches, CDNs, F5's Redis cache) key on the **full URL**. Two different `template=` values are two different cache keys. If you put presentational stuff in the path, you bloat cache cardinality ("two views of the same data" for every template); if you put resource identity in the query, you get the opposite problem. The "restful" instinct — path = noun, query = adjective — exists because HTTP-aware caching *is* URL-sensitive. This is a cache-design decision wearing an aesthetic costume.

### 1.2 View counters: "atomicity" and the durable-drain pattern

The doc's counter is `INCR views:{username}` — and the *reason* it's safe is the single-threaded Redis serialization from the f5_f6 notes. But the *durability* question is separate: **Redis counts live in RAM; the number survives until Redis restarts.** For a "nice touching number" that's fine. For a number that "must be auditable," it isn't — and that's why professionals use the **fast-write / batched-persist** pattern:

```
Every view  → Redis INCR (microseconds, atomic, cheap)
             ↓ periodically
Flush job   → read Redis count → UPDATE db.setting (single durable write per batch)
             → (optionally RESET the Redis counter so a restart loses ≤1 window)
```

Why not just `UPDATE views += 1` in SQLite/Database on every view? Because that's a **write per view** — on a single-writer DB that's a serialized bottleneck; on Redis it's one atomic op on one fast server. The trade-off: durability per-view (DB) vs constant-cost writes under load (Redis) — and "a counter is *nearly* right for a while, then flushed" is the sweet spot. This is the exact pattern the reference app's Cloudflare KV used, and it's how virtually every "views" counter on the internet works.

The key insight to *feel*: **the counter value you *show* in the response is the pre-increment value** (the doc's "starts reflecting next time"). That's not a bug — it's what happens when you count *after* serving, because you chose not to block the response on the increment. You've deliberately traded "exact current count" for "fast response." Knowing *which* trade you're making is the senior part.

### 1.3 What `BackgroundTasks` actually does (and its limits)

"Queue it, don't await it" hides a precise mechanism. FastAPI's `BackgroundTasks` (Starlette's, really):

- collects `add_task(callable, *args)` entries during the endpoint,
- **sends the response to the client first** (the entire point: the client isn't blocked),
- then runs each queued task — synchronously, in order, *in the same process*.

Two mechanisms worth knowing:

1. **It's not a real task queue.** There's no separate worker, no retry, no persistence. If the process dies after the response went out but before the task ran, the task is *lost*. Fine for "count a view," wrong for "email the user the reset link" (you'd want a durable queue). The doc's rule of thumb — light/best-effort here, queue for heavy/critical — is the correct boundary.

2. **It runs *after* the response, in the same event loop.** For a CPU-heavy background task (say a 2-second Pillow render in F8), a `BackgroundTasks` entry runs *on the event loop and blocks it* — every other request meanwhile waits. "Background" here means "after the response," **not** "off the event loop." That distinction only matters from F8 onward, where CPU work is *the* topic.

Also note: `background.add_task(...)` still runs **in the request's database session lifetime if you use it wrong** — Starlette starts background tasks after the response but within the same request cycle, so a session that's already closed (via `get_session`'s `yield` teardown) can't be used safely inside a background task. If your background task needs a DB session, it must open **its own**. This is the classic "background task + DB" footgun, and it only appears when you combine features.

### 1.4 URL state reaches the frontend — the `location.search` mechanism

Not strictly F7 (the frontend is F9), but the mechanism underpins "shareable":

`window.location.search` is the part of the URL after `?`. The browser exposes the parsed query (and `history.pushState` in F9 can change the URL *without a page reload*). The *entire* "share" story is: read URL → derive state → render; write state → update URL. Because the URL is the source, a "share" is just "paste the URL," and a "refresh" is "re-run the whole read-URL → render pipeline." No server-side persistence of "view settings" needed. This is why query-param state differs from in-memory/`localStorage` state: **it lives in the address bar and survives a copy-paste to anyone.**

A pragmatic warning for later (F9+): query-parsing is *dirty*. `location.search` is a string; you split on `&` and `=`, decode `%20`, handle missing/malformed params, and defend against dupes. This is why "URL state" libraries exist (`URLSearchParams`). Cargo-cult risk: assuming the query always has exactly the shape *you* put there. It won't — users bookmark, share, and hand-type URLs.

### Field notes — Feature 7

> **⚠️ Counters can be "counted twice" by a refresh — that's a feature, not a bug... unless you need unique views.** `INCR` counts *loads*, and browsers reload aggressively (cache-busting, retries). For "this portfolio was opened N times," load-counting is right. For "N *people* saw it," you need a different key per visitor (e.g., a hashed cookie/anon ID), which is a product decision, not a counter decision.

> **⚠️ `BackgroundTasks` and *async* tasks.** Starlette runs sync background tasks in a threadpool and *async* ones on the loop. If you `add_task` an `async def` that does slow CPU work, you're queueing it *onto the loop* (see 1.3). If you need async+safe, use the threadpool via a sync wrapper or a real queue. A `print()` here makes this visible in the logs.

> **📌 This is the feature where you first feel F5's seam paying rent.** If you built F5's `dependencies/counters.py` as a separate module, F7's "increment shared across landing + stats" is a *call, not a copy-paste*. Reusing a concern in two places is the actual test of whether the seam was well-placed.

> **📌 Keep the counter's *serialization* as the only place that defines the key names (`views:` / `total:`).** If two modules invent slightly different key strings, your counter silently counts into two different buckets — and it never "fails," just wrong-numbers.

## Part 2 — Feature 8: Export (PNG/PDF, streaming, CPU offload)

### 2.1 The event loop vs CPU: the mechanism behind "respect the loop"

The async premise (F2) is: **one thread runs the event loop; every `await` lets it switch to something else.** The cost you don't always hear: *a synchronous chunk of CPU work occupies that one thread for its full duration.* While `render_png` churns through pixels, the loop cannot even look at the network sockets of *other* requests — requests pile up, TCP buffers fill, clients time out. It's not that the render is slow; it's that **the loop is single-threaded, and CPU work is un-spliceable.** I/O work yields at `await` points; CPU work has no yield points.

`asyncio.to_thread(render_png, ...)` fixes this by running the callable in a **thread** from the executor pool, while `await` lets the loop continue. The mechanism of `to_thread`: it submits the callable to the loop's default `ThreadPoolExecutor`, returns a future, and you `await` it. The loop is free; the render occupies one thread; when the thread finishes, the future resolves and your coroutine resumes.

The honest caveat (GIL): Python's **global interpreter lock** means pure-Python threads don't run *simultaneously* — but a single `to_thread` render *does* free the loop thread, which is the entire point here. `to_thread` isn't parallelism magic; it's **"move the blocking off the loop thread."** (This is also why the "synchronously-slow, non-GIL-releasing" C-extension case needs extra care — not relevant yet.)

The *rule* the doc gives — "no CPU work directly in an `async def`" — is exactly this mechanism compressed. When would you *not* need it? A sync `def` route (FastAPI runs those in the threadpool already — see f1_f2 §2.1). The moment your route is `async def`, CPU work inside it blocks the loop by definition.

### 2.2 `Content-Type` vs `Content-Disposition` — two headers, one lie each

Headers are how HTTP tells a client what to do with a body, and *two* of them are involved here:

- **`Content-Type: image/png`** — a statement about *what the bytes are*.
- **`Content-Disposition: attachment; filename="x.png"`** — a *suggestion about how to treat it*: `inline` = "show me," `attachment` = "download me," plus the proposed filename.

Why does a "download" need both? Because the browser's decision — *render inline vs save to disk* — is driven by the disposition header, while *how to decode* is driven by the content type. And the filename in disposition overrides the URL's filename (which may be a route like `/export/octocat/png` with no `.png` at all). If you want "download as `octocat-portfolio.png`, not `png`," you *must* send disposition.

The security flavor of this header: the `filename` parameter is **attacker-shaped data in a response header**. A `filename="octocat"; name="bob"` or a newline injected into it can break the header (header injection) or mislead a download. The doc's "username is alphanumeric already, but sanitize anyway" is *exactly* right — this is defense-in-depth on a place where a legit-looking username could carry `\r\n` sneaked past your regex on some other path.

### 2.3 `StreamingResponse` — when it's needed and when it isn't

The doc uses `StreamingResponse(BytesIO(png), ...)`. The mechanism: Starlette streams the *iterable* chunk by chunk to the client instead of buffering the entire response in memory. That matters when the payload is *generated incrementally on the server* (a huge file, a live event stream) or too big to hold whole.

The honest notice: **a small `bytes` object is not that case.** Returning `Response(content=png, media_type="image/png", headers=...)` would also work and would be simpler. The pedagogical value of `StreamingResponse` is F8's stated one — *learning* streams, which you'll genuinely need in F12/F13 (big CSVs, live metrics). But don't cargo-cult it: **if you already hold the full content, plain `Response` (or `FileResponse` for on-disk files) is the right tool.** Choosing the simplest correct response type is the professional move. `FileResponse` vs bytes is the same trade (reuse the file from disk/nginx vs send what Redis gave you).

### 2.4 Cache the *artifact*, not just the data

F4/F5 cached the *JSON*. F8 introduces caching the **generated file** — the PNG for a username is deterministic, so rendering it once and re-serving is pure waste (CPU + the upstream calls to build the data). `Cache-Control: public, max-age=900` plus a Redis `png:{username}` key is the mechanism: **expensive-to-compute artifacts are cacheable if deterministic.** The step the doc pushes to an exercise (store PNG bytes in Redis) is the senior-habit form of "cache the result, not just the inputs." Any immutable, deterministic transform (an image, a PDF, a thumbnail, a chart) is a candidate.

> Pattern to recognize: this is the *same* cache-aside shape as F4/5 — check key → miss → compute → store → serve. The *unit* changed (from "profile JSON" to "PNG bytes"), the mechanism didn't. Recognizing that "new feature = same pattern, new key" is how you stop writing bespoke code everywhere.

### Field notes — Feature 8

> **⚠️ `asyncio.to_thread` and heavy work under a request.** The default threadpool has a limited size. If users hammer `/export` with many simultaneous PNG renders, every worker thread gets busy and *new* `to_thread` calls queue behind them — so under load, even `to_thread` can stall. The doc's Step-9 "move heavy renders to a background queue, return 202 + job_id" is the *scaling* answer to that. The boundary to remember: to_thread for occasional/short CPU work, a queue when it's frequent/heavy.

> **⚠️ Header injection into `Content-Disposition`.** If username could ever contain `"`, `\r`, or `\n`, the filename breaks the header (CR/LF ends the header line early — server-side header injection). Your F2 username regex blocks those, but "validated at the route, injected in a *different* route that forgets" is a real bug family. Sanitize at the *boundary of the header*, not only at the input boundary — belt and suspenders, deliberately.

> **⚠️ "It's PNG — but is it *readable*?"** Returning bytes with `image/png` while the bytes are garbage (a failed render wrote empty bytes, or you passed a Pillow `Image` object instead of `bytes`) gives the browser a broken `image/png` download with no error in *your* logs. Test that the bytes actually decode (`PIL.Image.open(BytesIO(png)).verify()`) — F11's exercise 3 is exactly this.

> **📌 `Pillow` isn't a PDF engine.** Pillow can *save* a single-image "PDF," but a real multi-page/vector PDF is a different tool (ReportLab, WeasyPrint, headless Chrome). The doc's "PDF via Pillow" is a teaching shortcut; the "real-world upgrade" (render HTML → PDF) is in Step 8. Knowing the line between "demo of the pipeline" and "production PDF rendering" saves a nasty surprise later.

> **📌 The filename must match what the user expects to download.** `content-disposition: attachment; filename="octocat-portfolio.png"` is user-facing — it's the file name in their Downloads folder. It's a tiny detail that users *absolutely* notice and judge. It also happens to be the field where injection lives, so treat it with both care and respect.

## Closing note

F7's background tasks are "after the response, in process, no retries" — a cheap way to defer *light* work and the exact shape to *not* reach for when work is heavy or critical. F8's `to_thread` is the memory-killer version of the same instinct applied to *CPU* — you don't gain parallelism, you gain "the loop stays responsive." And both features are, quietly, one running theme: **cache and defer are the two ways to keep "fast" from turning into "expensive under load."** When you hit a real production latency problem, these two mechanisms — cache the deterministic, defer the independent — are usually the first two places a senior looks.
