## Part 1 — Logging, Middleware & Request Correlation

### 1.1 Why `print()` is not logging — the mechanism of a structured log

`print("user:", u)` writes text to stdout. Your F1-F12 dev workflow read that in a console. The moment production happens, three things break:

1. **Volume** — millions of lines scroll you out of the window. You need *machine-readable* output for grep, dashboards, and alerts.
2. **Correlation** — a single user's request touches uvicorn, FastAPI, the client, Redis, the DB. A bare `print` has no way to connect "I fetched a user" to "the request that timed out." The fix that F13 uses — a **`request_id`** added to every line — is a *correlation key*: every log entry carrying `request_id=abc` is one request's full journey, even if separated by 50,000 other lines. That's exactly what you'll do in support: grep the whole log for one id.
3. **Levels** — `INFO` vs `WARNING` vs `ERROR` vs `CRITICAL` is the *signal* that lets a monitoring stack decide what to alert on. A print-based app has no such separation.

Mechanically, `logging` is a **pipeline**: `Logger` (you call it) → `Handler` (where it goes: stdout, file, JSON formatter) → `Formatter` (how it's shaped). The `extra={...}` dict in F13's middleware isn't just decoration — it's how a *structured* (key=value/JSON) formatter picks up fields. Turning "plain text log" into "JSON lines" is one Formatter swap, and that's why the stdlib choice scales to real tooling (Loki/Datadog) with zero code churn.

### 1.2 Middleware — the mechanism of "runs for every request"

FastAPI/Starlette middleware is a **filter chain** around the request/response: each middleware wraps the whole app. The signature `async def dispatch(request, call_next)` is the giveaway — `call_next` is literally "pass the request *down* the chain and get back the response." Order of `add_middleware` calls defines nesting order (last-added is outermost, so it runs *first* on the request path and *last* on the response path — the "onion" model).

Why is middleware the *right* home for cross-cutting concerns (logging, security headers)? Because those concerns apply to **every** endpoint — request id, timing, and headers have no business in a route. Contrarily, rate limiting (F5) was *not* middleware, because it applies only to expensive endpoints. The discriminating question is "**every** request, or **some** requests?" — if every, middleware; if some, a dependency or a guarded route. That's not taste; it's the difference between "a concern that can't forget any endpoint" and "a concern with a narrow blast radius."

### 1.3 `BaseHTTPMiddleware` vs pure-ASGI middleware — one honest caveat

F13 uses `BaseHTTPMiddleware` (the convenient Starlette base class). There's a known performance caveat: `BaseHTTPMiddleware` introduces a small extra hop (it wraps your dispatch in an awaitable Task), and historically had edge cases with streaming bodies and background tasks (Starlette docs + a well-known discussion cover this). For *this* project's logging/headers, it is completely fine and far more readable.

The point to *know* (not act on yet): **the "clean, simple" abstraction has a real but small cost, and the pure-ASGI form (a callable nested around the app) is the performant alternative.** A senior recognizes both forms and picks per need — convenience-under-budget wins here; raw-ASGI matters when profiling says the hop matters. Knowing the distinction prevents the "it's slow under load, must be the middleware... no it isn't" misdiagnosis later.

### 1.4 Logging without leaking — the "never log secrets" rule, mechanically

The F13 rule "never log passwords/tokens/full bodies" isn't paranoia — it's *because logs outlive requests*. Logs are: shipped to central stores, kept for months, piped into tools that may surface them, copied into bug reports. A password in a log line is a permanent record *anywhere a debugger looks*, long after the request that needed it. Two mechanisms protect you: (1) *never put secrets in what you log* at the source (don't log `password`), and (2) sanitize/redact at the *formatter* (some teams scrub known key names even if a dev does log them). The doc's "secrets in config, not code, not logs" is the whole spine: **secrets should exist in exactly one place (the injected environment), and never be re-published by the app.**

### Field notes — Feature 13

> **⚠️ Middleware order matters for headers too.** Each middleware adds headers when returning the response upward. A middleware's *own* response-level setup must happen after `await call_next`. Adding security headers in a middleware you mounted *inside* another middleware still works, but always set headers on the way *back* (post-`call_next`) using the *response object you return*, not by mutating `request`. Violating that = headers silently missing on error responses.

> **⚠️ "One structured log line per request" is a goal, not a result.** Background tasks (F7), exception handlers, and dependency teardown all log *outside* the middleware's timer window — so one request can yield 3+ lines with the same `request_id` but different durations. That's expected; the `request_id` makes them *correlatable*, not singular. Don't "fix" it into one line — you'd lose the task logs that are the actual debugging value.

> **⚠️ Logging the request *path* can leak query-string/PII.** `request.url.path` (F13's log) intentionally excludes `?query` — good. Logging `request.url` *with* the query can leak tokens shared in URL parameters. Preferences vary; the safe default is path-only, and always sanitized.

> **📌 Timeouts are a request, too.** If your app hangs (a dead lock, a slow upstream), the middleware *never logs the completion line* — so "a missing completion log for `request_id=X`" is itself a diagnostic ("this id never finished"). Monitoring stacks alert on id-aged > N for exactly this reason. Start having `request_id` findable in *every* log line, and this diagnostic becomes free.

## Part 2 — Security Headers, CORS, Health & Metrics

### 2.1 Each security header defends a *specific attack*

Headers are cheap to add and each one pairs with a concrete vulnerability class:

- **`X-Frame-Options: DENY`** — defends **clickjacking**: an attacker embeds *your* page in an invisible `<iframe>` on *their* site and lures clicks ("like", "delete"). `DENY` tells every browser "never render this document inside a frame." Mechanism: the header is parsed by the browser *before* framing (CSP's `frame-ancestors` is the modern, also-supported replacement).
- **`X-Content-Type-Options: nosniff`** — defends **MIME sniffing**: some browsers, when `Content-Type` is missing or ambiguous, *guess* the type by content. A polyglot file served as `text/html` gets executed as HTML — `nosniff` forces the browser to trust the declared type. Mechanism: one declaration removes an automatic, attacker-influenced decision.
- **`Content-Security-Policy: default-src 'self'`** — a **safeguard and an accelerator**. CSP is a policy that says "the only origin allowed to load subresources (scripts, images, styles) is this same origin" — so even if an injection slips past your frontend escapes, the browser refuses to execute a `script` from `evil.com`. It also *locks in* current behavior (a huge refactor that adds a CDN script must declare it or warn).
- **`Security Headers` beyond these** (HSTS, `Referrer-Policy`, permissions-policy) are the extensions of the same idea: each one *removes a browser-behavior decision* that a hacker otherwise gets a vote in.

The cargo-cult version is "add these 5 headers to look professional." The understanding version: **each header is a specific, named, testable defense you can explain with the attack it stops.** When asked in a review "why does the CSP exist?", the answer is "which attack does it disarm."

### 2.2 CORS — the browser's *reading-room* rule

CORS is misunderstood constantly. The mechanism: **an HTTP *request* is not blocked by CORS — the browser's *JavaScript reading the response* is.** A cross-origin `fetch` still *reaches* your API (bots, curl, other servers are unaffected). What CORS governs is whether the *browser* lets `window.fetch`/`.then(data => ...)` see the response, and whether the browser *sends* credentials (cookies) with it. It exists because browsers enforce *origin separation*: without it, a malicious site's JS could silently read *your* logged-in user's data.

That's why:
- `allow_origins="*"` is dangerous specifically when combined with **credentials** (browsers forbid `*` with `credentials: true` — and a `*`-allowed un-credentialed API is still readable by any site).
- the doc's "your real frontend origin" is precise: the header tells the browser "this other origin is *allowed to read our responses*" — you list *your own* frontend, no one else's.
- the F9/F10 "works from curl, fails in browser" almost always *is CORS*: curl has no origin policy, the browser does.

The F13 config (`allowed_origins` in `Settings`) is the correct shape — **CORS becomes configuration, not in-code magic**, so a frontend changing origin doesn't require an app diff.

### 2.3 Health checks — what they are *for* (and their limits)

`/healthz` returning `{"status":"ok"}` is tiny but its *consumer* is an orchestrator or load balancer (Docker `HEALTHCHECK`, k8s probe, Cloud Load Balancer). Mechanism: the runtime polls the endpoint; a non-2xx (or timeout) marks the instance **unhealthy** → it's *drained* (traffic stopped) and *restarted*. That's the whole contract: **`/healthz` is a yes/no the platform uses to decide whether this instance should keep getting requests.**

The F13 upgrade — "`/healthz` checks DB *and* Redis" — raises that from "the process is up" to "the process can actually *serve*." If Redis is down, the instance is returning 503 *even though the process is alive* — and the orchestrator restarts it / the LB routes around it. The *senior caveat*: a health check that's *too* eager (checks DB latency on every probe) can make a busy-but-fine instance look unhealthy and get *flapped* (restart loop). Health = "can I serve requests *now*" — checking dependencies is right; adding latency-sensitive work to the probe is a footgun. Similarly, `/metrics` (Prometheus-format counters) is *for reading + alerting*, not a "check" — it's how you see *what's happening* (rates, errors, latency) rather than only *whether it's alive*.

### 2.4 Fail-fast on misconfig — the mechanism of "defaults are allowed in dev, refused in prod"

F13's checklist item "fail fast if `jwt_secret` is the default and not `debug`" is a *specific* instance of a general rule: **never let a dangerous default run silently in production.** The mechanism: a config check at startup — `if not debug and settings.jwt_secret == "change-me-in-prod": raise` — converts "a silent, always-wrong secret" into «a loud, immediately-caught error.» Same pattern applies to `DEBUG=True` in prod, `api_keys` left blank, CORS `*`, `.env` not loaded. Each one is a line at app-start that *forces the operator to be consciously non-default*. The alternative — discovering the misconfig at 3am after a breach — is the cost this line is buying you out of.

### Field notes — Feature 13

> **⚠️ CORS `allow_origins="*"` is a footgun worth an explicit "no".** Combined with `credentials=True` the browser *rejects* the combination; with no credentials it lets *any* site read responses. Setting `*` "just to make it work in dev" and inheriting it into prod is a real, repeatable incident. The right dev-time answer is a *localhost* allow-list or a Vite proxy (F10), not `*`.

> **⚠️ Gate the API docs in prod, but don't *store* them in prod-visible places.** `docs_url=None` when `debug=False` turns off the interactive API *viewer* — the OpenAPI spec still exists if explicitly requested. That's not a security boundary (the API is enumerable by probing), but removing the *convenient* discovery surface is still right practice. Declare it in config, not a `# TODO` comment you'll forget.

> **⚠️ The security *checklist* is the artifact.** F13's Step 6 table (every check + where + what to do if violated) is the *repeatable* lesson — reviewers run it, you run it at every deploy, and CI can *eventually* automate parts. Log it, keep it current; a checklist nobody runs is decoration, but a checklist that gates a merge is enforcement (the F12 philosophy, applied to security).

> **⚠️ Don't log the *entire* body even "temporarily."** Once a token/password touches a log store, it's *there* (backed up, indexed, retained). "Just for debugging, one message" is how permanent leaks happen. Make redaction a default, not an exception.

> **📌 `request_id` is the one piece of this feature that repays you every day.** Wire it from day one; propagate it into the client/DB layers *later* if you ever need distributed tracing (F13's Step 9). Even without that, "grep one id across the whole log" is the difference between a bad day and a mystery.

## Closing note

F13 is the rare feature where most of the machinery was *already in place* — the F5 rate limiter, the F2 error shape, the F4 config layering — and the feature is mostly about **installing the observability and the attitude**. Each piece has a precise consumer: middleware's timer and `request_id` are for *you debugging tomorrow*; the security headers are for *the attacker you're removing a decision from*; `/healthz` and `/metrics` are for *the platform that runs the app*. Nothing here changes the app's behavior for a normal user — that's the whole point of "hardening." When you ship the next project, these are the lines you'll reach for *first* (structured logging, fail-fast config, security headers), not last — because every one of them is cheap-to-add-early and expensive-to-retrofit.
