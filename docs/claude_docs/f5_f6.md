## Part 1 — Feature 5: Redis + Rate Limiting

### 1.1 What Redis *is*, and why it can be atomic where SQLite couldn't

Redis is a **separate program** — a networked key-value store that holds data in RAM. But the thing that makes it atomic for counters is a design detail most tutorials skip: **Redis is single-threaded.**

Every command (`GET`, `SET`, `INCR`, `EXPIRE`) runs on one thread, one after another. There's never a moment where two clients' `INCR` for the same key execute *simultaneously* — the server processes command 1 fully, then command 2. That serialization is what "atomic" means here: **an operation that cannot be observed mid-way by any other client.** `INCR` is "read the value, add 1, write it back" — three steps that, on a database with multiple writers, could race. On Redis's single thread, they can't.

Contrast with SQLite in F4: multiple reader processes, but *one writer* with a lock. The lock is *how* SQLite serializes. Redis doesn't need a lock because it's already one-threaded — serialization is free, built into the architecture. This is why `INCR` "just works" for counters and rate limits across any number of app processes: the atomicity lives in the *server*, not in your code.

> Apply this when you read F6's "token denylist in Redis" and F7's "view counter": each is "a key that only Redis ever mutates," relying on this same single-thread serialization.

### 1.2 TTL — expiry is not a background cleaner; it's checked lazily

`SET key val EX 900` says "delete this key in 900 seconds." The mechanism worth understanding: **Redis doesn't actually run a timer that deletes the key at 900s.** Expired keys are removed lazily — on *access*, Redis checks `SET`/`GET` time and returns nothing if past expiry. (There's also a periodic "active expiry" pass that samples keys so memory doesn't leak, and `volatile-lru`/`noeviction` policies for full memory — but the *contract* to you is: expired = value missing.)

Why does that matter? Because **"the key is gone" and "the key was deleted 1 second ago" are indistinguishable to a reader.** Your `get_cached` returning `None` doesn't tell you if data was *never* stored or *just expired*. That ambiguity is exactly right for a cache (both mean "miss, go refetch"), but it's why you can't treat `None` as a signal of anything other than "not a hit."

### 1.3 Rate limiting: fixed-window vs sliding-window vs token-bucket

The doc calls out fixed-window's flaw and offers two alternatives. Here's the *mechanism* of each, so the trade-off is real, not a vocabulary test:

- **Fixed window** (`INCR key` + `EXPIRE key 60`): every request increments; the limit resets when the window does. Flaw: a "burst boundary" — 30 requests at second 59 of window A, then 30 at second 1 of window B = 60 requests in 2 consecutive seconds *around* a window edge, blowing past a 30/min limit. The burst-boundary is because "the window" is anchored to *server* clock, not to *when the user started*.

- **Sliding window**: instead of one counter resetting at a fixed boundary, you keep a log of recent request timestamps (a Redis **sorted set** — `ZADD` a scored member per request, `ZREMRANGEBYSCORE` to drop old ones, `ZCARD` to count) and the limit is enforced at the *current instant*: "how many in the last 60s *right now*." No boundary hole. Cost: more commands, more memory, more code per request.

- **Token bucket**: a bucket holds up to `capacity` tokens; each request spends one; tokens refill at `rate` per second. Mechanism: *burst allowance with debt smoothing* — an idle user has a full bucket (can burst `capacity` immediately), and the refill rate caps sustained load. Costs: you must store "current tokens + last refill timestamp" and compute the refill on read (no way to schedule a refill). Redis can do this with a small **Lua script** to keep check-and-spend atomic (a script runs on Redis's single thread, giving you multi-command atomicity that a client round-trip can't).

The senior habit: **pick the algorithm by the *abuse shape* you fear** — fixed window is fine for "slow down a demo"; sliding/token-bucket matter when a burst genuinely can cost you money or quota.

### 1.4 Dependency-as-gate vs middleware — where does the check belong?

The doc says "use a dependency on the costly endpoints." The mechanism of the two options:

- **A dependency** only runs when an endpoint that *declares it* runs. You control which endpoints are guarded.
- **Middleware** runs for **every** request to the app, before routing. Broad by nature.

Rate-limiter-in-middleware would count `GET /` and `/docs` traffic in the same budget you're protecting for `/portfolio` — pointless and confusing. Dependency-on-endpoint puts the gate exactly where the cost is. This "narrowest blast radius" instinct is the same one behind F3's service layer and F5's swap-proof repository interface. You'll see it everywhere if you look for it.

### 1.5 Why the F4 refactor made F5 a one-file swap

In F4, the docs had you define `ProfileCacheStore` as a `Protocol` — an **interface** — and made the service depend on the *interface*, not the concrete SQLite repository. In F5, you rewrite the repository body, keeping the same `get_cached`/`save` signatures, and the service doesn't change.

That's **Dependency Inversion in action**: high-level policy (service "if fresh serve, else fetch") depends on an abstraction (the store interface), and low-level details (SQLite vs Redis) implement that abstraction. The mechanism is structural: the service holds a *name* of what it needs (`get_cached(username) -> dict | None`), and any implementation that satisfies the name plugs in. No branch on "if I'm using Redis, do X."

The thing to *feel* here: the interface was invented one feature *early* (F4), looking forward (F5). That backward-looking-layering is the pattern — you build seams *before* you need the swap, so the swap is cheap when the need arrives.

### Field notes — Feature 5

> **⚠️ Redis doesn't purge by default — `decode_responses=True` isn't about caching.** If you omit `decode_responses=True`, Redis returns `bytes`, not `str`. `json.loads(b'{"a": 1}')` fails loudly. Getting bytes is *technically* correct for Redis but wrong for your JSON handling. It's a one-flag fix that saves a surprising amount of debugging — and it's also your first taste of "the client library's defaults are not your product's defaults."

> **⚠️ `request.client.host` can be a proxy.** Behind a reverse proxy or load balancer (F12/F13!), every request may look like it comes from the proxy's IP — all users share one source, so one user's over-limit can 429 everyone. The real client IP is typically in `X-Forwarded-For` (set by the proxy). Trusting `client.host` blindly is a real-world bug that shows up exactly when you deploy.

> **⚠️ Redis counter "lost on restart" is expected — it's RAM.** The doc is honest about it: Redis persistence (RDB/AOF snapshots) is *opt-in by default config*. A plain dev Redis forgets counters on restart. That's *correct* for a cache/rate-limit (you WANT counters to reset when you restart?) — the moment you need durability, that's F7's flush-to-DB job or enabling persistence.

> **📌 `INCR` returns the new value — you can use that return in the same round-trip.** The doc's rate limiter does `count = await r.incr(key)` and then branches on it. Using the *return value* is one network round-trip, and it never requires a `GET` first. This is "return-value APIs" showing up in Redis, not just in Python.

## Part 2 — Feature 6: Authentication (Hashing + JWT)

### 2.1 Why passwords are hashed (and what a hash is, mechanically)

A **hash** is a function with a one-way property: easy to compute, infeasible to invert. `hash(password)` is a fixed-length string with no practical path back to `password`. So the DB stores the hash; a login attempt computes `hash(candidate)` and compares to the stored hash — no plaintext ever rests in the DB.

But "some hash" isn't enough. Two failures your F6 has to defend against:

1. **Fast hashes are brute-forceable.** MD5/SHA-256 are fast — that's their purpose — which makes them *fast to try* for an attacker. bcrypt is **deliberately slow** (a work factor that repeatedly re-hashes — "key stretching"). A single bcrypt compare takes ~100ms; guessing a password becomes thousands of times more expensive. That slowness *is* the security.

2. **Deterministic hashes are rainbow-table-able.** If the same password always hashes to the same value, an attacker can precompute a table of common-password → hash. **Salt** fixes this: a random value per user appended before hashing, so the same password produces different hashes for different users. The salt is *not secret* — it's stored alongside the hash (bcrypt embeds it in the string: `$2b$cost$salt$hash`). Its job is unique-ness, not secrecy.

> ⚠️ bcrypt's 72-byte password limit: longer passwords get silently truncated by bcrypt's design. Reasonable apps cap password length anyway (`max_length` in the schema) so truncation can't produce a "different but accepted" password.

### 2.2 JWT — "a signed claim," mechanically

A JWT is three base64url segments joined by dots: `header.payload.signature`.

- **header**: `{"alg": "HS256", "typ": "JWT"}` — what algorithm and what type.
- **payload**: the claims — `{"sub": "bob", "exp": ts, "iat": ts}`. "sub" is the subject (user), "exp" the expiry timestamp.
- **signature**: a keyed hash of `header.payload` using the secret — `HMAC-SHA256(secret, header.payload)`.

The *why-it-works*: the signature is computed **over the payload** using a secret the server holds. If anyone modifies the payload (change `sub` to admin), the signature no longer matches, and the server (which recomputes the signature on verify) rejects it. This is a **message-authentication** property — integrity + origin, not secrecy. The payload is *readable by anyone* who decodes base64url (it's not encrypted!). A JWT's contents are public; only its *authenticity* is protected.

Two JWT design choices to internalize:

- **`exp` is a timestamp, not a boolean.** The client doesn't "expire" a token; the server *checks* `exp` against the current time on every decode. No server-side state is involved — the token carries its own death date.
- **"Stateless" = no lookup, but also no remote revocation.** Verifying a JWT is pure math — any server in a fleet can do it without a DB call. The flip side: a leaked token is valid until `exp`; the *only* ways to kill it early are a denylist (Redis) or short expiries + refresh tokens (the F6 exercises).

### 2.3 `OAuth2PasswordBearer` — what it actually reads and why 401 is automatic

`tokenUrl="/auth/token"` doesn't validate anything by itself. What it does: tells FastAPI "*this app expects the client to send `Authorization: Bearer <token>`*" and generates the **Authorize** button in `/docs` pointing at the login form. As a dependency, it reads the header and returns the token *string* (or raises a `401` automatically if absent).

The mechanism of the protected-route chain (which is what makes a route "protected"):
`route declares Depends(get_current_user)` → FastAPI resolves `get_current_user` → which itself declares `Depends(oauth2_scheme)` → which either returns the token or 401s → `get_current_user` decodes + verifies + loads User → or 401s. **The endpoint only runs if the whole chain succeeds.** This is the "guard at the door": the endpoint can assume a valid user without writing any auth logic. The layering here — *auth as a dependency chain, not as if-statements inside every route* — is the F3 service-layer instinct applied to security.

### 2.4 401 vs 403 — and the message-information-doesn't-leak rule

- **401 Unauthorized** = "I don't know *who* you are." Missing token, invalid token, expired token. The response includes `WWW-Authenticate: Bearer` — it's *an invitation to provide credentials*.
- **403 Forbidden** = "I know who you are, and you're *not allowed* to do this." Wrong owner, insufficient permission.

The doc's login returns 401 for both "user doesn't exist" and "wrong password" *on purpose*. Reason: if you returned 404 for "no such user" and 401 for "wrong password," an attacker could probe *which usernames exist* by observing the error code. Returning the same 401 either way prevents username enumeration. This "make the error messages symmetric" instinct generalizes — it's why some APIs return the same generic error for both. (F7's ownership check introduces 403: a *validly logged-in* user hitting someone else's resource.)

### 2.5 "Never store what you can derive": the hashed_password leak-safety lesson

The F6 refactor (Step 9) is about one thing: `UserOut` must **exclude** `hashed_password`. Mechanically, Pydantic models *only* serialize declared fields, and `response_model=` further filters — so a schema that doesn't declare `hashed_password` physically cannot leak it. But the *habit* to absorb is deeper: **defense against accidental exposure is a real, non-exotic threat class.** A senior writes the schema so that *nothing but the intended fields can possibly appear*, rather than relying on "I just won't put it in the response dict." This is the same "response_model as a filter, not documentation" point from the f1_f2 notes.

### Field notes — Feature 6

> **⚠️ `passlib` + new bcrypt versions emit a warning** ("error reading bcrypt version") — a known incompatibility between `passlib==1.7.4` and `bcrypt>=4.1`. Not fatal, but if you see it, it's a warning meaning "bcrypt detection failed"; either pin `bcrypt` < 4.1 or accept the warning. (Or switch to `bcrypt` directly — the `CryptContext` is a convenience, not a requirement.)

> **⚠️ `passlib[bcrypt]` and the venv — install `passlib` *with* the `[bcrypt]` extra** as written. Installing plain `passlib` gives you a package that *claims* bcrypt support but shells out to a backend you didn't install; you get an import error at *the moment the module it's lazily loading* is first used. The `[bcrypt]` extra is the actual dependency.

> **⚠️ `OAuth2PasswordRequestForm` (the login form in `/docs`) requires `python-multipart`.** FastAPI needs a form-parsing library to read `username`/`password` from `application/x-www-form-urlencoded`. Forgetting this dep = `500` or a multipart import error at the very endpoint you're trying to test. It's the #1 "why is my /docs Authorize button broken" cause.

> **⚠️ Never put a real `jwt_secret` in a committed file.** The F6 config default `"change-me-in-prod"` must be overridden by `.env`/env var. Polluting git history with a secret has a *long* half-life — rotate it, don't just "remove it later." (F13's checklist — "fail fast if `jwt_secret` is the default and `debug=False`" — is about turning this from a silent risk into an audible one.)

> **⚠️ JWT "aud"/"iss" claims are ignored by FastAPI's default `decode`** unless you validate them. Switching `decode` to `decode(..., audience="...")` and issuer checks is a hardening step; most tutorials skip it. Not urgent — but it's the difference between "has signature" and "was *meant for this app*."

> **📌 Tokens live your HEADER, not the URL** — and never in logs. The Browser's `Authorization: Bearer ...` never goes into a URL (which browsers/histories/proxies may log). The F13 rule "never log full bodies" exists partly for this. It's a normalization you build, not an accident you avoid.

## Closing note

Redis is a *single-threaded, atomic, RAM-based* store — and its entire design (INCR, TTL, key expiry) falls out of that one property. Rate limiting is *an algorithm choice* (burst boundary vs burst smoothing) hiding behind a `Depends()`. Password hashing is *about making brute-force expensive*, and JWT is *a public, authenticated claim that dies on a timestamp* — no encryption, no revocation, by design. Every one of these becomes trivial to misuse the instant you forget *which property* it gives you. Nothing here changes what you build next — but when a rate limiter mysteriously lets a burst through, or a "forgot password" flow leaks which accounts exist, you'll know exactly which mechanism is at fault.
